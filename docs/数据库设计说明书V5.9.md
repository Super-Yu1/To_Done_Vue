### 1.2 设计原则

1. **单库单机**：不做分库分表、不做读写分离——**百人量级用不上**（库总量 ≤2GB，见 10.2），一切以「够用且好维护」为准。
2. **一份脚本即全部**：表结构只有一个来源——根目录的 `todone.sql`。改表就改这一份、手工执行，
   不使用迁移工具，不保留变更历史（理由与纪律见第 9 章）。
3. **逻辑删除优先**：用户可见的删除一律是软删除；物理删除只发生在两处——**用户主动删除**
   （清空回收站、移除配图、换头像时淘汰旧图）与**回收站满 90 天的定时清理**（见 7.4）。
4. **结构与唯一性下沉到数据库，业务取值留给应用层**：`NOT NULL` / `UNIQUE` / 部分唯一索引照写不误
   ——那是结构与唯一性；但**枚举取值与数值范围不写 `CHECK`**（V5.7 起）：`status` / `priority` /
   `sort_order` 的合法取值由后端枚举 + 入参校验保证。理由与「不建外键」同源——**改一个枚举值
   不该要动 DDL**，校验集中在应用层才好维护。
5. **引用完整性留给应用层**：数据库**不建任何外键**，父子关系的存在性与级联删除由后端在事务内保证（见 3.3）。
6. **索引服务于已知查询**：每个索引都必须对应一条真实存在的查询，不留「可能有用」的索引。

## 2. 设计约定

### 2.1 命名与结构

| 项 | 约定 |
| --- | --- |
| 表名 / 字段名 | 全小写 + 下划线，如 `app_user`、`deleted_at` |
| 主键 | 统一命名 `id`，类型 `UUID`，默认值 `uuidv7()` |
| 引用列 | 命名 `<被引用实体>_id`（如 `user_id`、`biz_id`），类型与被引用主键一致（`UUID`）；**不建物理外键** |
| 唯一约束 | `uk_<表>_<字段>` |
| 检查约束 | `ck_<表>_<字段>` |
| 索引 | `idx_<表>_<字段缩写>` |
| 保留字规避 | 用户表命名 `app_user`（`user` 是 PostgreSQL 保留字）；任务表避开 `order`、`group` 等 |
| 字符集 | UTF-8（集群初始化时指定） |

### 2.2 数据类型选型

| 场景 | 选用 | 理由 |
| --- | --- | --- |
| 主键 / 引用列 | `UUID` + `DEFAULT uuidv7()` | PostgreSQL 18 内置 `uuidv7()`，其前 48 位是毫秒时间戳，**生成值时间有序**，插入时 B-Tree 的写局部性与自增整数接近；同时具备全局唯一、无需回查数据库、不暴露业务量级（不像 `BIGSERIAL` 会从 ID 看出总量）的优点。**不用 `uuidv4()`**：纯随机会打散索引页，写放大明显 |
| 有长度语义的字符串 | `VARCHAR(n)` | 长度上限本身就是一条业务约束，交给数据库兜底；同时给出更优的存储估算 |
| 自由文本 | `TEXT` | 任务描述长度不可预期。PostgreSQL 的 `TEXT` 与 `VARCHAR` 性能无差异，且无需前置长度声明 |
| 时间 | `TIMESTAMP`（无时区） | 应用与数据库同机同容器、统一 `Asia/Shanghai`，用 `TIMESTAMPTZ` 反而引入双重转换的歧义 |
| 布尔语义 | 语义化时间戳代替 | 如「是否已删除」用 `deleted_at`，比 `is_deleted` 多携带「何时删的」这一信息，且无需两个字段 |
| 枚举 | `VARCHAR(32)`，**不加 `CHECK`** | 不用 PostgreSQL 原生 `ENUM`（增删取值都要 DDL），也**不用 `CHECK`**（改一次取值还是要 `DROP/ADD CONSTRAINT`）。取值合法性由**后端枚举 + 入参校验**保证（V5.7 起）：库里只保留结构与唯一性，业务取值不进库——见 1.2 原则 4 与 6 章 |
| 计数 / 大小 | — | **本项目没有任何计数或大小类列**：验证码的尝试计数随表迁到 Redis，文件字节数 `size_bytes` 已在 V4.4 删除（图片统一在前端压缩后上传，库侧不记大小） |

### 2.3 主键生成

DDL 侧统一写 `id UUID PRIMARY KEY DEFAULT uuidv7()`，**主键由数据库生成**。MyBatis-Plus 侧映射：

```java
@TableId(type = IdType.AUTO)
private UUID id;
```

`IdType.AUTO` 在这里的语义是「**插入时不写 id 列，由数据库生成后回填**」：MyBatis-Plus 会带上
`useGeneratedKeys`，PostgreSQL 驱动通过 `INSERT ... RETURNING` 把 `uuidv7()` 的生成值取回来。
全局默认值在 `application.yml` 中配置：`mybatis-plus.global-config.db-config.id-type: AUTO`。

> **绝不要用 `IdType.ASSIGN_UUID`**：它在应用层生成的是随机 UUID（非时间有序），会打散索引页，
> 与选 `uuidv7()` 的初衷完全相悖。
>
> 数据库保留 `DEFAULT` 的意义：即使有人绕过应用直接写库（导入、订正脚本），也不会出现空主键。

### 2.4 审计字段

| 表 | 创建时间列 | `updated_at` | 说明 |
| --- | --- | --- | --- |
| `app_user` | `created_at` | ✓ | 会原地更新显示名、邮箱、手机号、密码，以及被管理员冻结 / 解冻 / 注销（注销后不再变更） |
| `task` | **`recorded_at`** | **✗** | **列名与其他表不同**：它可由用户在编辑时刷新，见下 |
| `user_avatar` | `created_at` | **✗** | 一用户一行，换头像 = 删旧插新，见下 |
| `task_image` | `created_at` | **✗** | 行基本不变，**只有 `sort_order` 会被重排**，见下 |
| `admin_user` | `created_at` | ✓ | 会原地更新名字、密码与 `last_login_at` |

**`task` 为什么叫 `recorded_at`、为什么没有 `updated_at`**

任务会被反复改（状态、优先级、描述）。"系统自动记下最后修改时间"对这个用途价值不大，
反而会让「这条任务是什么时候加进来的」变得不可信。于是把两件事合成一个**用户可刷新**的时间列：

- 列名叫 `recorded_at` 而不是 `created_at`——因为它并不总是"创建那一刻"：
  **编辑任务时由用户勾选是否把它刷新为当前时间（默认勾选）**，不勾则保持原值；
- 任务列表按 `recorded_at DESC` 排序，因此刷新时间等价于「把这条任务顶到列表最前面」；
- **没有 `updated_at`**：一个时间列就够了，两个反而要解释"哪个才是真的"；
- `recorded_at` 仍在插入时由应用写入 `now()`（列上也有 `DEFAULT now()` 兜底），只是更新时不自动改。

**`user_avatar` / `task_image` 为什么没有 `updated_at`**

两张表都遵循「**只增不更新**」：所有「修改」都表达为**删除旧记录 + 插入新记录**。

- `user_avatar`：一用户一行（`user_id` 唯一），换头像就是在同一事务里删掉旧行、插入新行；
- `task_image`：一个任务多行，保存任务时插入、编辑任务时移除的图删行 / 新增的图插行，保留的图不动。
  **图片随任务一起提交，落库时 `task_id` 必然已确定**，所以没有临时态，连 `status` 列都不需要；
  **唯一的例外是 `sort_order`**：拖动排序要求按新顺序重编号，这一列会被 UPDATE（见 4.4）。
  即便它变了也不给它 `updated_at`——那是「内容何时被改」的时间，排序不是内容变更，
  而且重排是整组一起动的，逐行记时间戳没有意义。

好处三条：省掉字段与「同一行被并发更新」的语义；每条记录从插入到删除中途内容不变；
与对象存储的行为天然对齐（MinIO 的对象也是不可变替换，而不是原地改写）。

**`created_at` 的写入方式**

| 机制 | 作用 |
| --- | --- |
| `NOT NULL DEFAULT now()` | **安全网**：绕过应用直接写库时不会留空 |
| MyBatis-Plus 自动填充：`@TableField(fill = FieldFill.INSERT / INSERT_UPDATE)` + `MetaObjectHandler` | 常规写入路径，业务代码不手动维护 |
| Service 层更新时不写 `createdAt` | 防止 `created_at` 被误改（`updateById` 传入的实体保持该字段为 null 即可） |

## 3. 实体关系

### 3.1 实体清单

| 表 | 用途 | 单用户 | 全站（≤500 账号，见 10.2） |
| --- | --- | --- | --- |
| `app_user` | 用户（可被管理员**冻结**或**注销**） | 1 行 | ≤ 500 行 |
| `task` | 待办任务（含已完成的与回收站中的） | 千级；已完成的永久保留，回收站中的满 90 天自动清理 | ≤ 50 万行 |
| `user_avatar` | 用户头像（**一用户一行**） | 1 行 | ≤ 500 行 |
| `task_image` | 任务配图元数据 | 千级（一个任务最多 9 张） | ≤ 15 万行 |
| `admin_user` | 管理员（后台管理用，**与用户表完全独立**） | — | 个位数 |

> **演示模式的数据不在库里**：未登录时的演示体验由前端内置的示范数据渲染，既不请求后端接口、
> 也不写数据库。因此本设计不包含演示账号，也不包含任何初始化业务数据——`todone.sql` 执行完，
> 库里是五张空表（管理员也不预置，由应用启动时引导创建，见系统说明书 7.11 / 11.3）。

### 3.2 关系说明

**数据库不建任何外键，全部引用关系由后端应用层维护。** 各关系的维护责任如下：

| 关系 | 类型 | 引用列 | 应用层维护方式 |
| --- | --- | --- | --- |
| `app_user` → `task` | 1 : N | `task.user_id` | 建任务时校验用户存在；**用户注销不删数据**（任务全部保留） |
| `app_user` → `user_avatar` | 1 : 1 | `user_avatar.user_id` | 上传时写入当前用户；**用户注销不删数据**（头像保留，管理员仍可见） |
| `app_user` → `task_image` | 1 : N | `task_image.user_id` | 上传时写入当前用户；**用户注销不删数据**（配图随任务保留） |
| `task` → `task_image` | 1 : N | `task_image.task_id` | 保存任务时插入，`task_id` 必然有值（图片随任务一起提交）；删任务时按 `task_id` 同步删除 |
| 验证码 | 不落库 | — | 存 Redis，与五张表无关联（见 7.3） |
| `admin_user` | **无关联** | — | 与其余四张表**没有任何引用关系**：管理员不"拥有"任何数据，所有操作都经后端写 `app_user` |

> **本期没有物理删除用户的路径**（注销只置 `deleted_at`，见 7.5），上面三行因此都不涉及真实删除。
> 若将来确实要做物理删除，顺序是「孙 → 子 → 父」：**先删配图对象与记录 → 再删头像记录与对象 →
> 再删该用户的全部任务 → 最后删账号**，全程不依赖数据库级联（本库没有外键）。

**应用层必须守住的四条约定**：

1. **写入前校验父行存在**：任何写入 `user_id` 的操作，先确认该用户存在（登录态已隐含此保证）；
2. **删除时显式处理子行**：删除用户 / 任务时，在同一事务内按「孙 → 子 → 父」顺序删除，不依赖数据库级联；
3. **删除任务只软删，不动物理行**：配图记录与对象保留，恢复任务后仍可见；
4. **自动清理只有一个**：回收站超期任务由唯一的定时任务清理（见 7.4）；其余数据一律不自动删除
   （验证码靠 Redis 的 TTL 到期消失）；孤儿数据靠巡检 SQL 发现（见 10.4）。

### 3.3 为什么不建外键

这是**全表统一策略**，不是某几张表的特例。

| 理由 | 说明 |
| --- | --- |
| 写放大与锁竞争 | 外键约束在每次写入子行时都要在父行上加共享锁并检查存在性。高并发写同一父行（如同一用户频繁建任务）时会产生额外锁等待。应用层在已登录态下校验则没有这个开销 |
| 级联行为不可控 | `ON DELETE CASCADE` 会在一次删除中隐式影响大量行，链路不可见，出问题时难以定位「到底删了什么」。应用层逐表显式删除，链路清晰、可分步、可记录日志 |
| 与软删除语义冲突 | 本系统大量使用软删除（任务进回收站）。外键约束只能约束**物理删除**，对软删除毫无作用——留着它反而制造「有人替我把关」的错觉。真正的删除规则（哪些子行该跟着删、哪些该保留）只有业务知道 |
| 数据订正与迁移自由 | 无外键时可直接批量修数、按条件导入导出、重建表，不必先解除约束再恢复，运维脚本简单很多 |

**代价与补偿**

| 风险 | 补偿措施 |
| --- | --- |
| 可能产生孤儿数据（引用不存在的父行） | ① 所有写操作在 Service 层校验父行存在；② 所有删除操作在同一事务内处理子行；③ 巡检 SQL 兜底（见 10.4） |
| 完整性靠代码自觉，缺少数据库层的最后一道防线 | 项目为个人独立开发，模块边界清晰、写入路径收敛，用约定替代约束更轻量。若将来需要这道防线，可补 `NOT VALID` 外键——先只约束新数据、不校验历史数据，避免上线时被存量脏数据卡住 |
| 排查问题时看不到关系图 | 依赖本文档第 3 章与附录 C 的表接口对照 |

**顺带一提**：V4.0 把原来的多态表 `file_object` 拆成 `user_avatar` 与 `task_image` 之后，
这五张表里已经**没有多态关联**了——每张表指向谁都是确定的（`task.user_id`、`task_image.task_id` 等），
`admin_user` 更是独立于其余四张表。
但"不建外键"仍是全库统一策略，理由见上表。

## 4. 表结构

### 4.1 app_user · 用户表

| 字段 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | UUID | N | `uuidv7()` | 主键 |
| name | VARCHAR(64) | N | | **显示名**；**不唯一**——登录不用它，仅用于界面称呼 |
| email | VARCHAR(128) | N | | **登录凭证**；未注销的行之间唯一；**统一转小写存储** |
| phone | VARCHAR(32) | Y | | 手机号，可为空；非空时未注销的行之间唯一；**本期不用于登录** |
| password | VARCHAR(128) | N | | BCrypt 密文（固定 60 字符，留冗余以便升级算法） |
| frozen_at | TIMESTAMP | Y | | **冻结时间**；非空即「账号已被管理员冻结」 |
| frozen_reason | VARCHAR(128) | Y | | 冻结原因，可为空；登录被拒时展示给用户 |
| deleted_at | TIMESTAMP | Y | | **注销时间**（软删除）；非空即「账号已注销」 |
| password_updated_at | TIMESTAMP | N | `now()` | 密码最后修改时间；**签发早于此值的 token 立即失效** |
| created_at | TIMESTAMP | N | `now()` | 创建时间 |
| updated_at | TIMESTAMP | N | `now()` | 更新时间 |

**约束**

| 类型 | 名称 | 定义 |
| --- | --- | --- |
| PRIMARY KEY | `app_user_pkey` | `(id)` |

> **邮箱与手机号的唯一性不在约束里**，而是两条**部分唯一索引**（见 5.1）：只约束 `deleted_at IS NULL`
> 的行——注销后立刻释放，同一个邮箱 / 手机号可被重新注册或绑定。**`name` 没有任何唯一性。**

**说明**

- **头像不在本表**：见 4.3 `user_avatar`。两处都不存 URL，只存 objectKey，
  换域名或调整访问路径时无需刷数据，URL 由应用按 `{publicBaseUrl}/{objectKey}` 拼接；
- **显示名只有一个字段 `name`**（V5.4 起，由 `username` + `nickname` 合并而来）：它**不唯一、不建索引**，
  必填但只用于界面称呼——系统没有社交场景（不搜人、不 @、不跳主页），不需要充当标识符。
  **登录只认 `email`，判重只认 `email` / `phone`**；去掉唯一性反而省下一个索引与一类冲突（1001 随之废弃）；
- **冻结用 `frozen_at` 而不是 `status` 枚举**：与 `task.deleted_at` 同一套路子——一个时间列同时表达
  「是否冻结」与「何时冻结」，比「布尔 + 时间」两个字段省事，也不必为两种状态维护 CHECK 约束。
  解冻即置回 `NULL`；`frozen_reason` 是可选的补充说明；
- **注销释放唯一键，数据全保留，而且不可恢复**：注销后该用户无法登录、token 立即失效；
  任务、配图、头像，以及 `email` / `phone` 的**原值**都原样留在行里，而两条**部分唯一索引**
  （`WHERE deleted_at IS NULL`，见 5.1）让这一行不再参与判重——同一个邮箱 / 手机号
  **立刻可以被重新注册或绑定**。两件事能同时成立，靠的是「把唯一性从约束挪到部分索引」，而不是改写数据；
- **为什么不做占位改写**（把注销行的 `email` / `phone` 换成随机 UUID）：那是"全表唯一约束"时代的做法——
  不把原值挪走就没法释放唯一键。现在唯一性由部分索引表达，**释放与保留原值能同时成立**，
  改写反而白白丢掉信息（排查"这个邮箱以前注册过谁"时尤其重要）。注销不可恢复之后，
  连"恢复时撞车"的顾虑也没有了，改写的最后一点动机也消失了；
- **为什么不做物理删除**：删用户要连带清掉他的任务、图片与 MinIO 对象，且无法撤销——
  这类应用里"停用"的需求远多于"销毁"（见系统说明书 1.2「不做」）；
- **注销没有 `deleted_reason`**：冻结的原因要展示给被冻结的用户，而注销的提示文案固定
  （「该账号已注销」），具体原因留在管理员操作日志里即可，不必落库；
- **`password_updated_at` 不是审计字段，而是失效开关**：JWT 无状态，改完密码后旧 token 本来到期前一直有效。
  拦截器校验时比对「token 的签发时间 ≥ 本列」，于是三种情况都会让旧会话立即失效——
  用户自己改密码、管理员重置密码、管理员改用户资料后要求重新登录（见系统说明书 7.11）。

| 字段 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | UUID | N | `uuidv7()` | 主键 |
| user_id | UUID | N | | 归属用户，**无外键**，由应用层保证有效 |
| title | VARCHAR(128) | N | | 标题 |
| description | TEXT | Y | | 详细描述 |
| status | VARCHAR(32) | N | `'TODO'` | `TODO` / `IN_PROGRESS` / `DONE` |

| completed_at | TIMESTAMP | Y | | 完成时间；非 `DONE` 状态时必须为空 |
| deleted_at | TIMESTAMP | Y | | **软删除时间**；非空表示在回收站 |
| recorded_at | TIMESTAMP | N | `now()` | 记录时间；创建时写入，编辑时可由用户刷新为当前时间 |

**约束**

| 类型 | 名称 | 定义 |
| --- | --- | --- |
| PRIMARY KEY | `task_pkey` | `(id)` |

> **没有 `CHECK`**：`status` 三选一、`priority` 四选一由后端枚举 + 入参校验保证（V5.7 起，见 1.2 原则 4）。

**说明**

- `deleted_at` 一个字段同时表达「是否删除」与「何时删除」：回收站列表要按删除时间倒序，
  计算剩余保留天数也要用它，比布尔标记更省事；
- `status` / `priority` 的取值**不在库里约束**：后端用 `TaskStatus` / `TaskPriority` 枚举承接，
  入参校验与 `@EnumValue` 映射一道把关；库侧只保证 `NOT NULL` 与默认值；
- `completed_at` 与 `status` 的一致性由应用层保证（状态机转换时同时写这两个字段），
  不用数据库触发器——触发器对排障不友好，且这份一致性逻辑本来就属于业务规则；
- `user_id` 上无外键，但**有索引**（见 5.1），因为「按用户查任务」是最高频的访问路径。

| object_key | VARCHAR(512) | N | | MinIO 对象键，全局唯一，**不含域名** |
| bucket | VARCHAR(64) | N | | 所在存储桶（留字段以便将来分桶） |
| original_name | VARCHAR(255) | Y | | 原始文件名，仅用于界面展示 |
| content_type | VARCHAR(128) | Y | | MIME 类型 |
| created_at | TIMESTAMP | N | `now()` | 上传时间 |

> 该表**没有 `updated_at`**：只增不更新，换头像 = 同一事务内删掉旧行、插入新行（见 2.4）。

**约束**

| 类型 | 名称 | 定义 |
| --- | --- | --- |
| PRIMARY KEY | `user_avatar_pkey` | `(id)` |
| UNIQUE | `uk_user_avatar_user_id` | `(user_id)` |
| UNIQUE | `uk_user_avatar_object_key` | `(object_key)` |

### 4.4 task_image · 任务配图表

| 字段 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | UUID | N | `uuidv7()` | 主键 |
| user_id | UUID | N | | 上传者，**无外键** |
| task_id | UUID | **N** | | 归属任务，落库时必然已确定；**无外键** |
| sort_order | SMALLINT | N | | 展示序号，同一任务内唯一，从 1 开始；**小的排前面** |
| object_key | VARCHAR(512) | N | | MinIO 对象键，全局唯一，**不含域名** |
| bucket | VARCHAR(64) | N | | 所在存储桶（留字段以便将来分桶） |
| original_name | VARCHAR(255) | Y | | 原始文件名，仅用于界面展示 |
| content_type | VARCHAR(128) | Y | | MIME 类型 |
| created_at | TIMESTAMP | N | `now()` | 上传时间 |

> 该表**没有 `updated_at`**：只增不更新（`sort_order` 除外，见 2.4）。

**约束**

| 类型 | 名称 | 定义 |
| --- | --- | --- |
| PRIMARY KEY | `task_image_pkey` | `(id)` |
| UNIQUE | `uk_task_image_object_key` | `(object_key)` |
| UNIQUE | `uk_task_image_task_sort` | `(task_id, sort_order)` **DEFERRABLE INITIALLY DEFERRED** |

> **没有 `CHECK`**：序号从 1 起、单任务 ≤9 张，都由后端保证（V5.7 起，见 1.2 原则 4）。

**说明**

- **没有 `status`**：图片随任务保存时一起提交，落库那一刻就已经挂在任务上，不存在
  「先上传、后绑定」的中间态。同理 `task_id` 是 `NOT NULL`；
- **序号在每次保存时统一重编为 `1..N`**：前端拖完顺序后，把「删图 + 加图 + 新顺序」一次性提交，
  服务端按最终顺序重写该任务的全部 `sort_order`。因此序号**始终连续、没有空洞**，支持拖动排序；
- **重排怎么过唯一约束**：`uk_task_image_task_sort` 是**可延迟**约束（`DEFERRABLE INITIALLY DEFERRED`），
  校验推迟到事务提交时——否则「`[A=1, B=2]` 换成 `[B=1, A=2]`」会在逐行 UPDATE 的中途就撞车；
- **`sort_order` 是该表唯一会被 UPDATE 的列**：改图仍是「删旧行 + 插新行」，内容列永远只写一次；
- **为什么用 `SMALLINT`**：单任务最多 9 张，`SMALLINT` 完全够用；序号 ≥1 与「单任务 ≤9 张」
  都由后端保证，库里不写 `CHECK`（见 1.2 原则 4）；
- 单任务 ≤9 张由应用层限制，**不落库**——数据库侧不建触发器去数数，避免每次写入多一次查询；

### 4.5 admin_user · 管理员表

| 字段 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | UUID | N | `uuidv7()` | 主键 |
| name | VARCHAR(64) | N | | **登录名兼显示名**，全局唯一（管理员没有邮箱登录通道） |
| password | VARCHAR(128) | N | | BCrypt 密文 |
| last_login_at | TIMESTAMP | Y | | 上次登录时间；从未登录为空 |
| password_updated_at | TIMESTAMP | N | `now()` | 密码最后修改时间，语义同 4.1 |
| created_at | TIMESTAMP | N | `now()` | 创建时间 |
| updated_at | TIMESTAMP | N | `now()` | 更新时间 |

**约束**

| 类型 | 名称 | 定义 |
| --- | --- | --- |
| PRIMARY KEY | `admin_user_pkey` | `(id)` |
| UNIQUE | `uk_admin_user_name` | `(name)` |

**说明**

- **为什么单独建表，而不是给 `app_user` 加一列角色**：两者的登录入口、token、权限模型完全不同，
  合表会让「用户」这一概念同时承担两套语义——每条用户查询都得额外带 `role = 'USER'` 条件，
  备份与迁移也多一层耦合。分开后 `app_user` 保持「业务用户」的单一含义，管理员表小而独立；
- **与 `app_user` 零关联**：不建外键、不共享字段。管理员不能"拥有"任务或图片，
  也不能拿管理员账号登录前端业务界面——两套 token 互不认（见系统说明书 7.11）；
- **`name` 唯一，因为它同时是登录凭证**（V5.5 合并）：管理员**用 `name` + 密码登录**（后台没有邮箱登录通道），
  所以这一列必须唯一；它同时也是后台顶栏显示的名字。**与 `app_user.name` 的差异是有意的**：
  用户的 `name` 只是称呼（可重名，见 4.1），管理员的 `name` 是账号标识（不可重名）——两张表别"顺手统一"；
- **只能 INSERT，不能 UPDATE / DELETE**：写入这张表的只有两处——应用启动时的引导创建（仅当表为空）
  与后台的**新增管理员**（见系统说明书 6.5 ⑫）；**没有任何修改或删除已有管理员的路径**
  （见系统说明书 1.2「不做」）。忘记密码只能手工改库，且必须**同时刷新 `password_updated_at`**，
  否则该管理员的旧 token 不会失效；
- `last_login_at` 供后台顶栏显示「上次登录时间」，是排查"是不是别人登过"的第一线索。

## 5. 索引设计

### 5.1 索引清单

| 索引 | 表 | 字段 | 类型 | 支撑的查询 |
| --- | --- | --- | --- | --- |
| `idx_task_user_deleted_status` | task | `(user_id, deleted_at, status)` | 普通 | 任务列表按状态筛选；各状态计数统计 |
| `idx_task_user_deleted_due` | task | `(user_id, deleted_at, due_date)` | 普通 | 按截止时间排序；逾期与今日到期统计 |
| `idx_task_user_deleted_recorded` | task | `(user_id, deleted_at, recorded_at DESC)` | 普通 | 主页瀑布流的默认排序（记录时间倒序，滚动分页加载） |
| `idx_task_trash` | task | `(user_id, deleted_at) WHERE deleted_at IS NOT NULL` | **部分索引** | 回收站列表 |
| `idx_task_image_user` | task_image | `(user_id)` | 普通 | **按用户统计图片总数**——保存带图的任务时要校验「该用户已有多少张图」（上限 5000 张），见 5.2 |
| `uk_app_user_email` | app_user | `(email) WHERE deleted_at IS NULL` | **部分唯一索引** | **登录凭证**唯一（仅未注销行，注销即释放）；注册 / 登录 / 换邮箱 / 找回密码都走它 |
| `uk_app_user_phone` | app_user | `(phone) WHERE deleted_at IS NULL` | **部分唯一索引** | 手机号唯一（仅未注销行，注销即释放）；**可为空，空值不参与唯一冲突** |
| `idx_email_code_*` | — | — | — | **已随 `email_code` 表一起移除**（验证码迁 Redis，其 TTL 与计数不再需要索引） |

主键（`id`）与唯一约束（`user_avatar` 的 `user_id` / `object_key`、`task_image` 的 `object_key` 与
`(task_id, sort_order)`、`admin_user` 的 `name`）已由约束自动建立索引，不重复列举；
`app_user` 的 `email` / `phone` 则由上面两条**部分唯一索引**负责（V5.2 起不再是约束）。
`uk_task_image_task_sort` **顺带取代了原先的 `idx_task_image_task`**：`(task_id, sort_order)`
既能按任务取图，又直接给出序号顺序，比 `(task_id)` 更合适。

> 由于取消了外键，`user_id` **不会**像有外键时那样自动获得索引。这里三个 `task` 索引的前导列
> 就是 `user_id`，已覆盖该需求；`user_avatar.user_id` 则由唯一约束自带索引，不必再建。
> `task_image.user_id` 原先**不建索引**（当时只有一个低频统计场景），但 V5.9 起它成了**高频校验路径**
> ——每次保存带图的任务都要数一次「该用户已有多少张图」（单用户 5000 张上限，见系统说明书附录 D），
> 没有索引就是全表扫描（全站 15 万行），因此补上 `idx_task_image_user`。

### 5.2 设计说明

**为什么 `deleted_at` 放在联合索引第二列**

软删除给每张表都加了「筛选条件」，但筛选条件是 `IS NULL`（正常）或 `IS NOT NULL`（回收站），
两个方向都要走索引。把 `deleted_at` 放在 `user_id` 之后、业务字段之前：

- 正常列表 `WHERE user_id = ? AND deleted_at IS NULL AND status = ?` → 前两列定位、第三列过滤；
- 回收站 `WHERE user_id = ? AND deleted_at IS NOT NULL` → 由专门的**部分索引** `idx_task_trash` 承担。

**为什么用部分索引**

回收站数据通常只占总量的一小部分。部分索引 `WHERE deleted_at IS NOT NULL` 只索引这一小撮行，
体积远小于全表索引，且回收站查询必然命中；而正常列表查询完全不会扫描到它。用一个廉价索引
换取回收站页面的稳定响应，很划算。

**为什么邮箱 / 手机号用「部分唯一索引」**

需求是「注销后立即释放唯一键，但注销行里的原值不能动」。三种做法里：

| 做法 | 为什么不选 |
| --- | --- |
| 注销时改写 `email` / `phone`（换成随机 UUID 或加后缀） | **破坏数据**：原值再也找不回来，与"数据全保留"直接冲突 |
| 另建一张"占用表"记录当前生效的邮箱 | 多一张表、每次查重多一次查询，为一个字段付出结构成本 |
| **部分唯一索引 `WHERE deleted_at IS NULL`** | **选它**：唯一性只落在"当前有效"的行上，注销行的原值不动、也不再参与判重 |

代价是它**不再是"约束"**：数据库不会阻止你插入两条 `email` 相同的**已注销**行（这正是要的效果），
所以应用层的查重必须写成 `WHERE email = ? AND deleted_at IS NULL`——漏掉后半句就会把已注销账号
误判成"已被占用"（见系统说明书 12 章）。`phone` 可空，而 PostgreSQL 的 NULL **天然不参与唯一冲突**，
所以不必为"很多人没填手机号"额外加条件。

**UUID 主键对索引的影响**

`UUID` 占 16 字节，是 `BIGINT` 的两倍，因此索引条目更大、单个索引页能容纳的键更少。
但由于 `uuidv7()` 时间有序，插入始终落在索引右端，**不会产生页分裂**，写性能与自增整数接近。
在「单用户千级任务、全站 50 万行」的量级下，索引体积差异可以忽略（见 10.2）。

**瀑布流为什么不动索引**

主页列表改为瀑布流（多列错落布局）只改变**展示**：查询仍是 `user_id = ? AND deleted_at IS NULL`
按 `recorded_at DESC` 排序、按页取数据，滚动到底加载下一页，走的还是 `idx_task_user_deleted_recorded`。
卡片高度不一致不影响数据库侧——分页以「条数」为单位而不是「屏数」，一页取多少条由前端定
（建议 20 条；取满即说明还有下一页，取不满即到底）。

**为什么没有 `priority` 的索引**

任务列表支持按 `priority` 排序（见系统说明书 6.5 ⑥），库里没有对应索引：单用户任务千级，
`user_id + deleted_at` 过滤后剩下的行本就不多，**内存排序即可**，多一个索引只是白增写入成本。
另外它是**业务权重排序**（低 → 中 → 高 → 紧急），由后端映射成数字后排序，**不是字典序**
——字典序会把"紧急"排到最后（见系统说明书 6.5 ⑥）。

**为什么没有 `keyword` 相关的索引**

关键字搜索是 `title ILIKE '%xxx%' OR description ILIKE '%xxx%'`，前置通配符无法走普通 B-Tree。
当前数据量（全站 50 万行级，见 10.2）下顺序扫描完全够用；若将来再上一个量级，再评估
`pg_trgm` + GIN 索引，本期不引入。

## 7. 数据生命周期

### 7.1 任务

| 阶段 | 数据状态 | 触发方式 | 对配图的影响 |
| --- | --- | --- | --- |
| 创建 | `deleted_at = NULL` | 用户新建 | 配图随任务一起插入（含 `sort_order`） |
| 完成 | `status = 'DONE'`，`completed_at` 有值 | 用户勾选 | 不变 |
| 软删除 | `deleted_at = now()` | 用户删除 | **保留**，恢复后仍可见 |
| 恢复 | `deleted_at = NULL` | 用户点击恢复 | 不变 |
| 彻底删除 | 记录被 `DELETE` | 用户手动（删除单条 / 清空回收站），或软删除满 90 天后由定时任务清理 | 先删 MinIO 对象，再删 `task_image` 记录 |

**已完成的任务永久保留**；回收站是「用户已删除、但还没决定彻底丢弃」的暂存区，
**软删除满 90 天后由定时任务物理删除**（连同配图，见 7.4）。

### 7.2 头像与配图（两张表）

**`user_avatar` —— 一用户一行**

| 动作 | 数据操作 | 说明 |
| --- | --- | --- |
| 上传头像 | 同一事务内 **`DELETE` 旧行 + `INSERT` 新行** | 提交后再删 MinIO 旧对象——反之可能出现头像 404 |
| 移除头像 | `DELETE` 行 + 删 MinIO 对象 | 用户没设头像时，就是"没有这一行" |

**`task_image` —— 一任务多行**

| 动作 | 数据操作 | 说明 |
| --- | --- | --- |
| 保存任务（新建 / 编辑） | 新增 `INSERT` + 移除 `DELETE` + **按最终顺序 `UPDATE` 全部 `sort_order`（`1..N`）** | 三步在同一事务内完成；语义是「这次保存后，配图就是这个样子」 |
| 编辑任务换图 | **`DELETE` 移除的行 + `INSERT` 新增的行** | 内容列永远只写一次，改图不写旧行 |
| 拖动排序 | **`UPDATE sort_order`** | 该表唯一的 UPDATE 场景；靠可延迟的唯一约束避免中途冲突 |
| 移除配图 / 任务彻底删除 | `DELETE` 行 + 删 MinIO 对象 | 任务彻底删除时按 `task_id` 批量删 |

> `user_avatar` 没有任何 UPDATE 场景；`task_image` 只有 `sort_order` 会被重写，因此两张表都不需要 `updated_at`（见 2.4）。
> 任务**软删除**时不触碰配图，恢复任务后图片仍可见（见 7.1）。

### 7.3 邮箱验证码（不入本库）

V3.0 起验证码迁到 **Redis**，本库没有对应表。留这一节只为说清「为什么它不在这里」：

| 判断 | 说明 |
| --- | --- |
| 数据特征 | 5 分钟 TTL、一次性消费、可丢失、无关联——本质是 KV，不是关系数据 |
| 原方案的成本 | 用 `status` + `expires_at` + `attempt_count` 模拟「存在 / 过期 / 计数」，另配 2 个功能索引 + 1 个清理索引 + 一条惰性清理规则 |
| Redis 的对应物 | TTL 自动过期、`GETDEL` 取出即删、Lua 原子比对与计数、`SET NX EX` 冷却、`INCR` 每日上限 |
| 一致性收益 | 图形验证码与邮箱验证码语义相同（短命一次性凭证），现在同住 Redis，不再一个在内存、一个在库 |

key 设计、Lua 脚本、限流与降级见《系统设计说明书》7.5。

### 7.4 回收站定时清理（全项目唯一的定时任务）

| 项 | 设计 |
| --- | --- |
| 实现 | `TaskCleanupJob`：`@Scheduled(cron = "0 30 3 * * ?")`，每天 03:30，启动类加 `@EnableScheduling` |
| 条件 | `task.deleted_at < now() - 90 天` |
| 动作 | 先删 MinIO 对象，再删 `task_image` 记录（按 `task_id`），最后删 `task` |
| 批次 | 每批 200 条、独立事务；单条失败记 ERROR 后继续，一条坏数据不阻塞整批 |
| 幂等 | 按主键删除，天然幂等，重复执行无副作用 |
| 配置 | `app.trash.retention-days`，默认 90 |
| 日志 | 每批记 INFO（条数 + 耗时），便于人工核对 |

单机单实例，无需分布式锁；应用没启动时任务不跑，下次启动照常补上（判据是 `deleted_at`，与执行次数无关）。

> 「删除 MinIO 对象」失败**只记日志、不阻断**：孤儿对象可事后用巡检脚本核对，
> 用户侧「删除成功」的确定性优先。

### 7.5 账号冻结、注销与密码重置（管理员操作）

这些操作**不改表结构、不删业务数据**，只写 `app_user` 的几个字段：

| 动作 | 数据操作 | 直接影响 |
| --- | --- | --- |
| 冻结 | `frozen_at = now()`、`frozen_reason = ?` | 登录被拒（1006，提示带上原因）；**已签发 token 立即失效** |
| 解冻 | 两列置回 `NULL` | 原密码照旧可用；任务、配图、回收站原样保留 |
| 注销（软删除，**终态**） | `deleted_at = now()` | 登录被拒（**1007**）；**已签发 token 立即失效**；数据保留，但**邮箱与手机号立即释放**，可被重新注册或绑定；**没有"恢复"**，要再用只能重新注册 |
| 重置密码 | `password = 新 BCrypt`、`password_updated_at = now()` | 旧 token 立即失效（签发早于该值），用户用新密码重新登录 |
| 改资料 | `name` / `email` | **会影响登录态**：邮箱是登录凭证，改动后一并刷新 `password_updated_at`，旧 token 立即失效、需用新邮箱重新登录（与系统说明书 6.5 ⑫ 对齐） |

- **冻结与注销都是「拒绝服务」，不是「删数据」**：用户的任务、配图、头像一律保留。
  区别在于**冻结可逆、注销不可逆**：冻结是临时的（带原因、可随时解除，解冻后完全回到原状），
  注销是"这个账号不要了"——一旦执行就没有回头路，要再用只能重新注册；
- **注销立即释放唯一键**：`email` / `phone` 的唯一性由部分唯一索引表达，只约束未注销的行，
  所以**同一个邮箱或手机号在被注销后立刻可以重新注册或绑定**；注销行里的原值原样保留
  （不做占位改写，见 4.1），只是"这个邮箱从此空出来了"；
- **不需要会话表或 token 黑名单**：过滤器本来就每次请求查一次账号（要拿最新 `name`、冻结与注销状态），
  顺便比对 token 的 `iat` 与 `password_updated_at` 即可，成本可以忽略（见系统说明书 7.11）；
- **管理员操作不落审计表，只写 INFO 日志**（操作人、目标用户、动作、时间）：
  单管理员场景下，一张审计表带来的价值不如它的维护成本，日志足够回溯（见系统说明书 10 章）。

## 8. 建表脚本

**脚本文件：根目录 `todone.sql`**（与本文档同目录）。这是本项目**唯一**的表结构脚本，手工执行，
不经过任何迁移工具（维护方式与执行命令见第 9 章）。文件里的建表语句与下面的完全一致，另带逐条 `--` 阅读注释。

> `todone.sql` 与下面的脚本**已经对齐**：**44 个字段**的 `COMMENT ON COLUMN` 全部到位（5 张表；V5.5 合并 `admin_user` 的两个名字字段后为 44），
> 文件里另有逐条 `--` 阅读注释。两份内容要一起改——改了表结构，两边同步。

```sql
-- ============================================================
-- To_Done · 数据库建表脚本
-- 适用数据库：PostgreSQL 18
-- 说明：
--   1. 主键统一 UUID + DEFAULT uuidv7()（PostgreSQL 18 内置，时间有序）
--   2. 不建任何外键，引用完整性由应用层维护（见数据库设计说明书 3.3）
--   3. 软删除：task.deleted_at 非空表示在回收站中
--   4. 五张表互不依赖，执行顺序任意
-- ============================================================

CREATE TABLE app_user
(
    id                  UUID         PRIMARY KEY DEFAULT uuidv7(),
    name                VARCHAR(64)  NOT NULL,
    email               VARCHAR(128) NOT NULL,
    phone               VARCHAR(32),
    password            VARCHAR(128) NOT NULL,
```

## 9. 脚本维护规范（手工执行）

### 9.1 为什么不用迁移工具

Flyway 这类工具解决的是「多人协作、多环境、变更历史可追溯」的问题：它用一张
`flyway_schema_history` 表记下每个脚本的版本号与 checksum，防止有人漏执行或偷改历史脚本。

本项目是**个人独立开发、单机单库、一次性交付**，这套机制的成本大于收益：

| 迁移工具提供的 | 本项目的实际情况 |
| --- | --- |
| 变更历史可追溯 | 只有一个人改，改了什么自己知道 |
| 多环境一致性校验 | 只有一套库，没有测试、预发环境要同步 |
| checksum 防篡改 | 没有第二个人可能改脚本 |
| 启动时自动执行 | 手工执行一次，几秒钟的事 |

代价是**没有自动化的变更记录**，只能靠纪律补：脚本是表结构的唯一真源，改完立刻执行，
并把变更同步回本文档（流程见 9.4）。

### 9.2 脚本位置与形态

| 项 | 约定 |
| --- | --- |
| 位置 | 项目根目录 `todone.sql`（与本文档同目录） |
| 形态 | **全量脚本**：描述「表结构现在是什么样」，含全部 5 张表 + 7 个索引（另有 5 个由唯一约束自动生成） |
| 内容 | 只有 `CREATE TABLE` / `CREATE INDEX` / `COMMENT ON`，**不追加 `ALTER` 语句** |
| 编码 | UTF-8 |
| 注释 | `--` 阅读注释 + `COMMENT ON` 数据库注释，两者都要（见第 8 章末尾） |

**为什么不把 `ALTER` 也写进文件**：文件是「当前结构」的快照，要能被整份执行来装一个全新的库。
一旦混进 `ALTER`，全新安装时会和 `CREATE TABLE` 里的定义打架（列重复、约束重名），
而在已有库上执行整份文件又会报 `already exists`。所以两件事分开做：

| 场景 | 怎么做 |
| --- | --- |
| 全新安装 | 整份执行 `todone.sql` |
| 已有库升级 | 手工写出并执行 `ALTER`，**再把这个变更改写进文件里对应的 `CREATE TABLE` 定义**，使文件重新等于当前结构 |

### 9.3 执行方式

```bash
# 全新安装：整份执行（在项目根目录）
docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" < todone.sql

# 已有库升级：只执行你手工写的那几条
docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" \
  -c "ALTER TABLE task ADD COLUMN remind_at TIMESTAMP;"

# 核对结果
docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" -c "\dt"      # 表
docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" -c "\di"      # 索引
docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" -c "\d+ task" # 字段与注释
```

**应用不碰表结构**：MyBatis-Plus 只做对象映射与 SQL 执行，不参与任何 DDL，因此没有也不需要
类似 JPA `ddl-auto` 的配置项。应用启动时也不会校验表结构——表没建好，会在第一次查询时报
`relation "task" does not exist`。

### 9.4 变更流程与纪律

| 步骤 | 动作 |
| --- | --- |
| 1 | 先备份：`pg_dump` 一份（见 10.3），改坏了能退回来 |
| 2 | 在库上执行 `ALTER TABLE ...` |
| 3 | 把 `todone.sql` 里对应的 `CREATE TABLE` 改成变更后的样子，保持「文件 = 当前结构」 |
| 4 | 同步更新本文档第 4 / 5 / 6 章，并在修订记录里记一笔（进位小版本、文件名同步更新） |

**三条纪律**：

1. **只做加法**：加表、加列（`NOT NULL` 必须带默认值）、加索引可以；删列、改类型、改名尽量不做，
   以免回滚时数据对不上（系统说明书 11.5 的回滚约定依赖于此）；
2. **动手前先看影响面**：某列被哪些查询、哪些索引用到，先在库上 `EXPLAIN` 验证一遍再改；
3. **改完立刻核对**：用 9.3 的 `\d+` 看一眼结果，别攒着。

## 10. 数据库运维

### 10.1 连接与参数

| 项 | 值 | 说明 |
| --- | --- | --- |
| 连接池 | HikariCP，最大 **20** / 最小空闲 2 | 按 **200 在线 / 20 QPS** 留余量（见系统说明书 11.1）；10 个其实也够，多出的留给慢查询与定时任务 |
| 连接超时 | 取连接 3 秒 / socket 30 秒 | 快速失败优于把请求挂住 |
| `max_connections` | 100（PostgreSQL 默认） | 后端池上限 20，加巡检与备份各占一两个，离上限很远 |
| `shared_buffers` | 512MB（起步档）/ **1GB（百人档）** | 其余内存交给操作系统页缓存；库总量在 1GB 量级，1GB 足够缓存热数据 |
| 容器限制 | 无显式内存上限 | 与 backend、MinIO 共享宿主机内存（起步 4GB / 百人档 8GB），靠 Swap 兜底突发 |

### 10.2 容量估算

按「**≥100 人同时使用 / ≤500 账号**」的规模定位算（见系统说明书 3.3）：

| 维度 | 估算 |
| --- | --- |
| 主键开销 | `UUID` 占 16 字节（`BIGSERIAL` 为 8 字节），每张表的 `id` 与每个引用列的存储翻倍 |
| 索引开销 | 因主键与 `user_id` 变宽，索引体积比 `BIGINT` 方案大约增加 **30%~50%**；但 `uuidv7()` 时间有序，写入不产生页分裂，性能无实质损失 |
| 任务数据 | 单条约 1.2KB（含 UUID 主键与引用列）。**全站上限 500 账号 × 人均千条 = 50 万行 ≈ 600MB**（含索引约 1GB）；已完成的永久保留，回收站中的满 90 天清理 |
| 图片元数据 | 单条约 0.5KB；`user_avatar` 每人一行（≤500 行），`task_image` 与图片数同阶（≤15 万张 ≈ 80MB） |
| 验证码 | **已不落库**：改存 Redis（`maxmemory 256mb` 封顶 + TTL 自动过期），对本库零占用 |
| 管理员 | `admin_user` 只有个位数行，**忽略不计**（单行约 0.4KB） |
| 库总量 | **≤ 2GB**（50 万任务 + 15 万图片元数据 + 索引 + WAL 与膨胀余量），单机内存放得下，`shared_buffers 1GB` 能缓存绝大部分热数据 |
| 磁盘大头是图片 | 15 万张压缩后的图（长边 1920、质量 0.85，单张约 300KB）≈ **45GB**；再加备份文件（`pg_dump -Fc` 约 300MB × 14 天 ≈ 4GB）仍以图片为主——**建议 100GB 盘**，60GB 约能容纳 5 万张以内 |

### 10.3 备份与恢复

| 项 | 策略 |
| --- | --- |
| 全量备份 | 每日 03:00 `pg_dump -Fc`，输出到 `/opt/to-done/backup/`，本机保留 14 天 |
| 异地备份 | 备份文件每日上传到对象存储或另一台机器，保留 30 天 |
| 备份窗口 | 库总量在 2GB 量级（见 10.2），`pg_dump -Fc` 通常十几秒完成，凌晨低峰执行无影响；图片另用 `mc mirror` 增量同步（见系统说明书 11.5） |
| RPO / RTO | RPO ≤ 24 小时，RTO ≤ 2 小时 |
| 恢复演练 | 上线后一个月内做一次完整恢复 |

```bash
# 备份
docker exec -i postgres pg_dump -U "$DB_USER" -Fc "$DB_NAME" \
  > /opt/to-done/backup/to_done_$(date +%F).dump
find /opt/to-done/backup -name 'to_done_*.dump' -mtime +14 -delete

# 恢复（--clean 会先删除同名对象）
docker exec -i postgres pg_restore -U "$DB_USER" -d "$DB_NAME" --clean \
  < /opt/to-done/backup/to_done_2026-09-20.dump
```

### 10.4 日常巡检

```sql
-- 连接数（接近上限需排查连接泄漏）
SELECT count(*) FROM pg_stat_activity WHERE datname = 'to_done';

-- 各表与索引占用
SELECT relname,
       pg_size_pretty(pg_relation_size(relid))       AS table_size,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
  FROM pg_stat_user_tables
 ORDER BY pg_total_relation_size(relid) DESC;

-- 索引使用次数（idx_scan 长期为 0 说明是冗余索引）
SELECT relname, indexrelname, idx_scan FROM pg_stat_user_indexes ORDER BY idx_scan;

-- 业务数据健康度
SELECT
  (SELECT count(*) FROM task       WHERE deleted_at IS NOT NULL) AS trash_count,
  (SELECT count(*) FROM app_user   WHERE frozen_at  IS NOT NULL) AS frozen_user_count,
  (SELECT count(*) FROM app_user   WHERE deleted_at IS NOT NULL) AS deleted_user_count,
  (SELECT count(*) FROM admin_user)                              AS admin_count;
-- 验证码不在库里，改看 Redis：docker exec -i redis redis-cli -a "$REDIS_PASSWORD" dbsize
-- frozen_user_count / deleted_user_count 应分别等于后台里"已冻结"/"已注销"的条数；
-- admin_count 正常是 1（个位数）

-- 孤儿数据检查（无外键，必须人工巡检）
SELECT
  (SELECT count(*) FROM task t
     LEFT JOIN app_user u ON u.id = t.user_id WHERE u.id IS NULL)        AS orphan_tasks,
  (SELECT count(*) FROM user_avatar a
     LEFT JOIN app_user u ON u.id = a.user_id WHERE u.id IS NULL)        AS orphan_avatars,
  (SELECT count(*) FROM task_image i
     LEFT JOIN app_user u ON u.id = i.user_id WHERE u.id IS NULL)        AS orphan_images,
  (SELECT count(*) FROM task_image i
     WHERE NOT EXISTS (SELECT 1 FROM task t WHERE t.id = i.task_id))     AS dangling_images;
```

**怎么读这几个计数**：`trash_count` 在用户清空回收站或定时任务跑完后下降，长期不降说明回收站清理没生效；
`frozen_user_count` 与 `deleted_user_count` 应分别与后台「已冻结」「已注销」列表的条数一致，
对不上说明有人绕过接口直接写库；`admin_count` 正常是 1（个位数），异常增长要立刻排查；
验证码不在库里（改看 Redis 的 `DBSIZE`，正常几十以内）。
**四个 orphan 计数应恒为 0**，一旦非 0 说明应用层的引用校验或删除逻辑有 bug，需立即排查。

### 10.5 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 执行脚本报「already exists」 | 在已有库上执行了整份 `CREATE TABLE` | 只有全新安装才整份执行；已有库只执行新增的 `ALTER`（见 9.2） |
| 巡检发现孤儿数据 | 应用层漏了父行校验或删除时的子行处理 | 先清理数据，再定位写入路径补上校验；这是取消外键后的主要代价 |
| 时间比预期早/晚 8 小时 | 列类型是 `TIMESTAMP`（无时区），应用与数据库时区不一致 | 统一容器与宿主机 `TZ=Asia/Shanghai` |
| UUID 太长不好人工排查 | 主键是 128 位 | 按 `created_at` 或 `id::text` 排序定位，`uuidv7()` 生成的 ID 本身按时间递增 |
| 列表查询没走索引 | 条件顺序与索引前导列不匹配，或 `deleted_at` 条件写成了 `OR` | 用 `EXPLAIN ANALYZE` 确认；确保查询是 `user_id 等值 + deleted_at IS NULL` |
| 回收站页面变慢 | `idx_task_trash` 缺失或被删除 | 重建部分索引 |
| 回收站越积越多 | 定时任务没跑（`@EnableScheduling` 未启用、应用长期停机，或日志里没有记录） | 查日志有无「回收站清理」INFO；确认那些行的 `deleted_at` 是否真的早于 90 天；必要时手工执行一次删除 |
| autovacuum 不回收空间 | 存在长时间未提交的事务 | 查 `pg_stat_activity` 中的 `xact_start`，终止异常事务 |
| 磁盘被日志或图片占满 | Docker 日志未轮转、图片对象与元数据持续增长 | 检查 `json-file` 轮转参数；按 10.4 的巡检结果清理无用图片（先删 MinIO 对象、再删 `task_image` 行） |

## 11. 附录

### 附录 A：字段类型速查

| 类型 | 使用场景 | 本项目实例 |
| --- | --- | --- |
| `UUID` | 主键与引用列 | 所有表的 `id`；`task.user_id`、`user_avatar.user_id`、`task_image.user_id`、`task_image.task_id` |
| `SMALLINT` | 小整数 | `task_image.sort_order`（单任务 ≤9 张，用 `INT` 是浪费） |
| `INTEGER` | 小范围计数 | 本期无实例（验证码的尝试计数已随表迁到 Redis） |
| `VARCHAR(n)` | 有长度上限的字符串 | `name(64)`、`title(128)`、`object_key(512)` |
| `TEXT` | 自由文本 | `task.description` |
| `TIMESTAMP` | 业务与审计时间（无时区） | `due_date`、`deleted_at`、`created_at`、`recorded_at` |

### 附录 B：保留字规避

| 冲突词 | 处理 |
| --- | --- |
| `user` | 用户表命名 `app_user` |
| `order` / `group` / `select` 等 | 未使用为表名或字段名；排序值若将来需要，命名为 `sort_order` |
| 约束名冲突 | 约束名自带表前缀（`uk_task_*`、`ck_task_*`），不会与其他表重名 |

### 附录 C：表与接口对照

| 表 | 主要读写的接口 |
| --- | --- |
| `app_user` | 用户侧：`/api/auth/register`、`/api/auth/login`、`/api/auth/password/reset`、`/api/users/me`、`/api/users/me/email`、`/api/users/me/password`；后台侧：`/api/admin/users/**`（改资料 / 冻结 / 解冻 / 注销 / 重置密码） |
