2. **两个接口前端没有使用**（已逐个核对，两边的封装都是「零调用方」，不是漏接）：

   - **`GET /api/tasks/{id}`**（说明书 6.4 #14，任务详情含配图）
     作用：按 id 取单条任务，字段与列表元素完全一致 —— 含 `images`（同样按 `sortOrder` 升序，说明书 6.5 ⑥ 末尾专门写了这点），供复用同一套渲染。
     为何没用：列表 `GET /api/tasks` 的元素**已经带全部字段**，编辑走「点列表行 → 弹窗」，直接用行数据即可；也没有「按 id 打开某条任务」的入口 —— 任务详情页、分享链接、通知跳转这些都还没做。
   - **`GET /api/admin/users/{id}`**（说明书 6.4 #27，用户详情，6.5 ⑫ 写明是「供详情抽屉展示」）
     作用：按 id 取单个用户，含四个数据量计数（在用 + 回收站）、冻结信息、头像直链。
     为何没用：后台用户列表的元素与它是**同一个 `AdminUserVO`**（字段完全一样），四个弹窗（编辑 / 重置密码 / 冻结 / 注销）只需要行数据 + id；后台也没有「用户详情抽屉」这个界面。`src/stores/admin.ts` 里的 `fetchUser` 是照接口写的，从未被调用。

   **是否建议后端删除：两个都建议保留，不建议删。** 理由是它们是各自资源路径的「读半边」—— `/api/tasks/{id}` 上已有 PUT / DELETE，`/api/admin/users/{id}` 上已有 PUT / PATCH / DELETE，只删 GET 会让 REST 语义残缺（同一条路径能改能删、不能读），后来接手的人必然要猜；而且各是一条已测通的查询，维护成本几乎为零，将来要加「用户详情抽屉」或任务深链时直接可用。
   若后端仍按「不留没人用的接口」想清掉，也可接受，但要**一次改齐**：说明书 6.4 #14 / #27、6.5 ⑥ 末尾那句详情与列表同构的说明、6.5 ⑫ 的用户详情段、附录 A 的错误码说明，以及前端 `src/api/task.ts` 的 `fetchTask`、`src/api/admin.ts` 的 `fetchAdminUser` 与 store 里的 `fetchUser`（三者都是零调用方，删除安全）—— 别只删后端，否则前端会留下会 404 的死封装。
