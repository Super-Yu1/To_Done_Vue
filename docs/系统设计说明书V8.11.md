## 1. 范围

### 1.1 定位与规模

**面向个人用户的多用户**待办管理 Web 应用：每个人管自己的任务——记录、配图说明、按优先级与截止时间跟踪、完成后归档、误删可从回收站找回。

**规模定位**：设计容量 **≥100 人同时使用**（见 3.3 的非功能指标）；**开放注册**，靠邮箱验证码 + 图形验证码当门槛。
后台由 **1~3 名管理员**运营，**只管账号**（冻结 / 注销 / 重置密码 / 改资料）——管理员**看不到任何人的任务与配图**，后台接口不读 `task` 与 `task_image`（头像属账号资料，可见，见 7.11 与 9 章）。

### 1.2 做与不做

**做**：账号（**开放注册**，邮箱验证码 + 图形码当门槛 / **邮箱登录** / 找回密码 / 更换邮箱 / 改密 / 头像 / **手机号绑定**）、任务（增删改查 / 状态流转 / 优先级 / 截止时间 / 配图 ≤9 张 / 搜索筛选 / 瀑布流列表）、回收站（软删除 / 恢复 / 彻底删除 / 清空，**满 90 天自动清理**）、图片（头像 + 配图，存 MinIO）、演示模式（未登录可体验，数据由前端内置）、界面（浅色 / 深色主题，默认跟随系统；列表与弹窗带动效过渡）、**后台（管理员独立登录 / 用户列表 / 冻结与解冻 / 注销 / 重置密码 / 修改用户资料 / 新增管理员）**。

**不做**：清单/分类、标签、子任务、任务依赖；多人协作、共享清单、任务指派、评论（**每人的数据只属于自己**）；移动端 App、小程序、桌面端；第三方登录、短信/扫码登录；周期任务、到期提醒、站内通知（邮件通道仅发验证码）；导出、数据看板、操作审计表；**短信通道与手机号登录**（手机号只作为唯一标识先存着，见 UC-09）；**管理员自助注册、对已有管理员的任何修改（改密码 / 改名 / 删除 / 停用）、用户的物理删除**（注销是软删除且**不可恢复**，见 UC-10 与 7.11）；**管理员查看用户的任务与配图**（头像属于账号资料、管理员可见；隐私边界见 7.11）。

## 3. 需求

**角色**：两种——**注册用户**（前台，写自己的数据）与**管理员**（后台，管理用户账号）。
两者账号独立、密钥独立、互不通用：用户 token 进不了后台，管理员 token 也写不了任务（见 7.11）。

### 3.1 功能需求

| 编号 | 用例 | 规则 |
| --- | --- | --- |
| UC-01 | 注册 | 输入**邮箱**、密码（**≥8 位且同时含字母与数字**，见 6.5 ③）、**名字**（显示名，**不查重**）、邮箱验证码、图形验证码；先过图形码 → 消费邮箱码（Redis）→ **只校验邮箱未被占用** → BCrypt 落库 → 签发 token；**落库部分单事务**（验证码不在事务内） |
| UC-02 | 登录 | **邮箱 + 密码 + 图形验证码**（用户名不再用于登录）；邮箱不存在与密码错误返回同一提示；被冻结 / 已注销分别返回 1006 / 1007 |
| UC-03 | 找回密码 | 邮箱 + 邮箱验证码 + 新密码；邮箱不存在时**也返回成功**（防账号枚举） |
| UC-04 | 更换邮箱 | 需登录；验证新邮箱未被其他账号占用 |
| UC-05 | 任务管理 | 标题必填；新建默认「待办 / 中」；切到已完成写 `completedAt`，切走清空；删除为软删除 |
| UC-06 | 回收站 | 显示删除时间与剩余天数；恢复即置空 `deleted_at`；彻底删除连同配图一起删；**满 90 天后由定时任务自动清理** |
| UC-07 | 图片 | 头像单张（前端裁成 1:1）；任务配图 ≤9 张；jpg / png / webp / gif，单张上传 ≤10MB，超阈值自动压缩后再存 |
| UC-08 | 统计 | 总数 / 待办 / 进行中 / 已完成 / 逾期 / 今日到期 / 完成率 / 回收站数 |
| UC-09 | 个人资料 | **名字**与头像直接改；**手机号可填可改（非空时全局唯一；本期不发短信、不用于登录）**；换邮箱需邮箱验证码；改密码需校验原密码、新密码同样**≥8 位含字母与数字**，改完强制重新登录 |
| UC-10 | 后台管理 | 管理员用**独立账号**登录（须过图形验证码）；用户列表分页 + 按**邮箱 / 名字 / 手机号**搜索 + 按状态（正常 / 已冻结 / 已注销）筛选；冻结（可填原因）/ 解冻；**注销（软删除，不可恢复）**；修改用户资料（名字 / 邮箱）；重置用户密码；**新增管理员**（已有管理员不可修改、不可删除，见 7.11）。**冻结、注销与重置密码都会让该用户已签发的 token 立即失效**；注销后**邮箱与手机号立即释放**（可被重新注册或绑定），而账号数据、任务与图片保留 |
| UC-11 | 演示模式 | 未登录用户可进入 `/demo` 体验完整界面，数据为前端内置示范数据 |

### 3.2 验证码规则

| 项 | 图形验证码 | 邮箱验证码 |
| --- | --- | --- |
| 形态 | 4 位字符 PNG（120×40，8 条干扰线） | 6 位纯数字 |
| 获取接口 | `GET /api/verify/captcha` | `POST /api/verify/email-code` |
| 存储 | **Redis**：`todone:verify:captcha:{captchaId}`（STRING） | **Redis**：`todone:verify:code:{scene}:{email}`（HASH：`code` / `attempts`） |
| 有效期 | 120 秒（Redis TTL 自动过期） | 5 分钟（Redis TTL 自动过期） |
| 一次性 | `GETDEL` 取出即删 | **Lua 脚本**原子完成「比对 → 删除」 |
| 失败上限 | 一次机会 | 5 次，超限即删（需重新获取） |
| 频次限制 | 无（可无限刷新，靠 Redis `maxmemory` 兜底） | `SET NX EX 60` 冷却；`INCR` + `EXPIREAT` 控每日 10 次 |
| 出现位置 | 登录、注册、找回密码、更换邮箱、发送邮箱码 | 注册、找回密码、更换邮箱 |
| 错误码 | 4001 | 4002 / 4003 / 4004 / 4005 / 4006 |
| 服务不可用 | 4007（HTTP 503） | 同左 |

邮箱验证码的三个场景：

| scene | 验证的邮箱 | 附加校验 |
| --- | --- | --- |
| `REGISTER` | 待注册的邮箱 | 该邮箱未被注册 |
| `RESET_PASSWORD` | 账号绑定的邮箱 | **不校验邮箱是否存在**（防枚举） |
| `CHANGE_EMAIL` | 待更换的**新**邮箱 | 需登录；新邮箱未被其他账号占用 |

### 3.3 非功能需求

| 项 | 指标 |
| --- | --- |
| 并发 | **≥100 人同时使用**——按 **200 在线 / 20 QPS** 设计单机容量，留了一倍余量 |
| 性能 | 单接口 P95 < 300ms（单用户最多 1 万条任务；所有列表查询必须走 `user_id` 索引，见 12 章） |
| 账号规模 | ≤ **500** 个注册账号（有上限即可，不做无限扩张） |
| 数据规模 | 任务 ≤ 50 万行、图片 ≤ 15 万张；**磁盘：图片 ≈45GB，建议 100GB 盘**（60GB 仅够 5 万张以内，见 4.3） |
| 可用性 | 99%；**单机单实例**，故障即中断，靠每日备份 + 快速重建兜底（见 4.4） |
| 兼容性 | Chrome / Edge / Safari 最近两个大版本；桌面优先，不做移动端适配 |

> 怎么从"百人同时使用"推出上面这些数：100~200 人在线、按人均每天几十次操作算，峰值 **20 QPS** 是个偏保守的估计；
> 性能侧真正要守的是**单用户万条任务时列表仍走索引**（这是唯一会随数据量劣化的路径）。
> 账号按 5 倍于同时在线人数预留（500），数据量按"每人千条任务、人均几张图"估——图片占磁盘的九成（见 4.3）。

## 4. 总体设计

### 4.1 设计原则

1. **极简优先**：功能能不加就不加，界面能少画就少画。
2. **前后端分离**：后端只提供 JSON 接口，前端独立构建，由 Nginx 聚合。
3. **约定优于配置**：统一响应、统一异常、统一分页、统一接口文档。
4. **数据隔离前置**：`@CurrentUserId` 强制注入，所有查询以 `userId` 为首要条件；删除一律软删除，
   **物理删除只有一处**——回收站超期清理（见 7.8）。
5. **外部依赖只走后端**：浏览器不持有 MinIO 凭证；表结构只认根目录 `todone.sql` 一份脚本（手工执行，不用迁移工具）。
6. **配置只放 `.env`**：账号、密码、密钥与一切可变设置都写在 `.env` 里（开发 `.env.dev`、部署 `.env.prod`，
   键名一致，见 11.2），代码与 yaml 只引用 `${变量}`；真实 `.env` 不进版本库（仓库里只放 `.env.example`）。

### 4.2 模块划分

| 模块 | 包路径 | 职责 | 依赖 |
| --- | --- | --- | --- |
| 通用 | `com.todone.common` | 统一响应、分页模型、业务异常、全局异常处理、审计基类 | 无 |
| 配置 | `com.todone.config` | 安全策略、CORS、MVC 扩展、OpenAPI、MinIO 客户端 | common |
| 安全 | `com.todone.security` | JWT 签发校验、认证过滤器、当前用户注入 | common |
| 验证 | `com.todone.verify` | 图形验证码、邮箱验证码（**存 Redis**）、Resend 发信 | common, security |
| 用户 | `com.todone.user` | 注册、登录、找回密码、资料、改密、换邮箱、头像 | common, security, file, verify |
| 任务 | `com.todone.task` | 任务增删改查、状态流转、统计、回收站 | common, security, file |
| 文件 | `com.todone.file` | 图片上传、对象存储读写、文件元数据 | common, security |
| 后台 | `com.todone.admin` | 管理员登录、后台用户管理（冻结 / 解冻 / 注销 / 改资料 / 重置密码）与**新增管理员**的编排 | common, security, user |

依赖单向：`admin → user → file / verify → security → common`（`task` 与 `admin` 互不依赖），无循环依赖。

**写 `app_user` 的代码只有 `user` 模块一处**：后台不直接操作用户表，而是调用 `user` 模块里的
`UserAdminService`（冻结 / 解冻 / 改资料 / 重置密码）。这样"用户表被谁改"永远只有一个答案，
也避免两处各写一份校验逻辑。

`verify` 是独立的基础能力模块，不认识「用户」概念，只按「邮箱 + 场景」处理验证码，因此可被注册、找回密码、更换邮箱复用。

### 4.3 部署形态

**单台** Ubuntu 22.04 LTS 云服务器，nginx / backend / postgres / minio / redis 五个容器
**直接 `docker run` 启动（不用 Docker Compose）**，只暴露 22 / 80 / 443。
容器清单、配置约定（两个 yaml + 两个 `.env`）与部署步骤见第 11 章。

| 档位 | 配置 | 适用 |
| --- | --- | --- |
| 起步 | 2C4G / 60G SSD / 2G Swap | 试用与 50 人以内；系统内存刚好（见 11.1） |
| **推荐** | **4C8G / 100G SSD / 2G Swap** | **百人量级**：JVM 提到 2G、PostgreSQL 1G，图片也有余量 |

**磁盘的瓶颈是图片而不是数据库**：库总量 **≤2GB**（50 万行任务 + 图片元数据 + 索引 + WAL 与膨胀余量，
见数据库说明书 10.2），而 15 万张压缩后的图约 40~50GB——60G 的盘要留意图片增长，建议 100G 起。

外部依赖只有 Resend（服务器出站访问 `api.resend.com:443`，无入站要求）。

应用内只有一个定时任务（回收站超期清理，见 7.8）；**单机单实例，不能水平扩展**——到容量上限只能升配（见 4.4）。

### 4.4 已知限制

已知的设计边界（不是待办清单）：单机部署无高可用，靠每日备份 + 快速重建兜底；回收站里的任务满 90 天会被自动清理，需要长期保留就得及时恢复；图片可被匿名读取（对象键含 UUID 不可枚举，需要私密时改为后端代理）；无 Refresh Token，过期需重新登录；**无账号锁定与失败计数**，接口层靠 Nginx `limit_req`（见 11.1）+ 图形验证码 + 强密码兜住；
**单机单实例、无法水平扩展**，到容量上限只能纵向升配；图片会被前端压缩（长边 1920、质量 0.85）并丢掉 EXIF，不保留原图；无操作审计**表**（管理员操作只有 INFO 日志）；后台**只能新增管理员，不能修改或删除已有管理员**（改密码要手工改库，见 7.11）；**用户只能被注销（软删除），不能被物理删除、也不可恢复**——注销后邮箱与手机号立即释放（可被重新注册或绑定），但账号行、任务与图片都保留，要彻底清掉只能手工改库；**手机号本期只存不用**（不发短信、不参与登录）。

## 5. 数据模型

系统共 **5 张表**：`app_user`、`task`、`user_avatar`、`task_image`、`admin_user`。验证码不落库（存 Redis，见 7.5）。

| 表 | 用途 | 关键设计 |
| --- | --- | --- |
| `app_user` | 用户 | **登录凭证只有 `email`**（未注销行之间唯一，部分唯一索引）；`phone` 可空、**非空时同样唯一**（本期不用于登录）；显示名只有一个字段 **`name`**（不唯一、不建索引，由 `username` + `nickname` 合并而来）；`password` 存 BCrypt 密文；**头像不在本表**；`frozen_at` 非空即「被管理员冻结」、`deleted_at` 非空即「已注销且不可恢复」（**注销即释放邮箱与手机号**，数据原值保留） |
| `task` | 待办任务（含回收站中的） | `deleted_at` 一个字段同时表达「是否删除」与「何时删除」；删除满 90 天后由定时任务物理清理 |
| `user_avatar` | 用户头像 | **一用户一行**（`user_id` 唯一），上传即绑定，没有临时态 |
| `task_image` | 任务配图 | 一任务最多 9 张；**随任务保存时一起提交**，落库即有 `task_id` 与 `sort_order`（展示顺序，从 1 起、小的在前；保存时可整体重编，支持拖动排序），没有临时态 |
| `admin_user` | 管理员 | **与 `app_user` 完全独立**：不建外键、不共享登录态；`name` **是登录名且唯一**（放 `app_user` 里它只是称呼）；没有自助注册——首个管理员由应用启动时引导创建（见 11.3），之后只能由**已登录管理员在后台新增**（见 6.5 ⑫），**已存在的管理员不可修改 / 删除** |

数据库为 PostgreSQL 18.6。**主键统一 `UUID DEFAULT uuidv7()`（时间有序）；数据库不建任何外键，引用完整性由后端应用层维护**。
表结构由根目录 `todone.sql` 一份全量脚本手工维护——MyBatis-Plus 只做映射与 SQL 执行，不参与任何 DDL。

**完整的字段定义、约束、索引、建表 DDL、数据生命周期与脚本维护规范见《数据库设计说明书》，此处不重复。**

## 6. 接口设计

### 6.1 规范

| 项 | 规范 |
| --- | --- |
| 风格 | RESTful，名词表示资源，动作用 HTTP 方法表达 |
| 前缀 | 统一 `/api` |
| 方法 | GET 查询、POST 新建、PUT 整体更新、PATCH 局部更新、DELETE 删除 |
| 请求体 | JSON（小驼峰）；文件上传用 `multipart/form-data` |
| 鉴权 | `Authorization: Bearer <token>` |
| 时间 | ISO-8601，如 `2026-10-01T18:00:00` |
| 图片传递 | 客户端只传**图 ID 或文件**：配图随任务接口的 `images` 段提交、更新时用 `imageOrder` 表达顺序；头像走独立接口。**响应里的 `url` 一律由服务端按 `objectKey` 拼接**，客户端不拼 URL |
| 文档 | 落在 Swagger 注解上（见 7.9），Swagger UI 是接口的权威描述 |

### 6.2 统一响应

```json
{ "code": 200, "message": "操作成功", "data": {}, "timestamp": 1758300000000 }
```

`code == 200` 表示成功；`data` 无内容时为 `null`。分页数据的 `data` 结构：

```json
{ "records": [], "total": 128, "page": 1, "size": 10, "totalPages": 13 }
```

| 码段 | 含义 |
| --- | --- |
| 200 | 成功 |
| 400 / 401 / 403 / 404 / 405 / 409 / 413 / 500 | 通用 HTTP 语义错误 |
| 1xxx | 用户模块 |
| 2xxx | 任务与回收站 |
| 3xxx | 文件与图片 |
| 4xxx | 验证码与邮件 |
| 5xxx | 后台管理（管理员登录，以及管理员对用户的操作） |

**约定**：业务失败返回 **HTTP 200 + 业务码**；网络/认证/权限/文件超限用真实 HTTP 状态码。完整清单见[附录 A](#附录-a错误码全表)。

### 6.5 关键接口

**① 图形验证码** `GET /api/verify/captcha` → `{ captchaId, image, expiresInSeconds }`，只下发 `captchaId` 与 Base64 图片，**答案留在服务端**。

**② 发送邮箱验证码** `POST /api/verify/email-code`

```json
// 请求
{ "email": "alice@example.com", "scene": "REGISTER", "captchaId": "8f3a...", "captchaCode": "A3F9" }
// 响应
{ "expiresInSeconds": 300, "resendAfterSeconds": 60 }
```

校验顺序：图形验证码（4001）→ 场景校验（REGISTER/CHANGE_EMAIL 查重，1002）→ 重发间隔 60 秒（4003）→ 每日 10 次上限（4004）→ 作废旧码 → **写 Redis** → 调 Resend（4006）。

**③ 注册** `POST /api/auth/register`

```json
{ "email": "alice@example.com", "password": "123456", "name": "爱丽丝",
  "emailCode": "483920", "captchaId": "8f3a...", "captchaCode": "A3F9" }
```

单事务执行：校验图形码 → 消费邮箱码 → **只校验邮箱未被占用（排除已注销账号，见 12 章）** → BCrypt → 建用户 → 签发 token。响应 `{ token, tokenType, expiresInMinutes, user }`。**`name` 不查重**（它只是称呼，登录只用邮箱）。

**密码规则（全站唯一一套）**：**最短 8 位，且必须同时包含字母与数字**。调用点有四处——注册、用户改密、
找回密码、管理员重置用户密码；校验集中在 `PasswordPolicy`（`common` 层），前端按同一规则提示并预校验。
格式不符统一返回 400（参数校验），不新开业务码。

**④ 登录** `POST /api/auth/login` → `{ email, password, captchaId, captchaCode }`，**只认邮箱**（用户名不再能登录），响应结构同注册。被冻结返回 1006、已注销返回 1007，两者都在**密码校验通过之后**才给出——否则登录接口就成了账号探测器。

**⑤ 找回密码 / 更换邮箱 / 修改资料**

| 接口 | 请求体 | 关键行为 |
| --- | --- | --- |
| `POST /api/auth/password/reset` | `{ email, emailCode, newPassword }` | 邮箱不存在也返回成功（防枚举） |
| `PUT /api/users/me/email` | `{ email, emailCode }` | 校验新邮箱未被**未注销**的账号占用后更新（1002） |
| `PUT /api/users/me` | `{ name?, phone? }` | 两个字段都可选，只改传了的；**`phone` 非空时校验未被未注销账号占用（1008）**，传空串即解绑；`name` **不做唯一校验**；本条**不影响登录态** |

**⑥ 分页查询任务** `GET /api/tasks`

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| page / size | int | 1 / 20 | size 上限 100（首页瀑布流一页 20 条） |
| keyword | string | | 标题或描述模糊匹配（忽略大小写） |
| status / priority | enum | | 状态、优先级筛选 |
| onlyUnfinished | bool | false | 只看未完成 |
| sortBy / sortDirection | string | recordedAt / DESC | 可排序字段：recordedAt、dueDate、priority。**`priority` 按业务权重排**（低 → 中 → 高 → 紧急），实现时映射成数字再排——`VARCHAR` 的字典序会把「紧急」排到最后 |

```jsonc
// data.records 元素
{ "id": "018f...", "title": "完成系统设计说明书", "description": "覆盖需求、架构…",
  "status": "TODO", "statusLabel": "待办", "priority": "HIGH", "priorityLabel": "高",
  "dueDate": "2026-10-01T18:00:00", "completedAt": null, "recordedAt": "2026-09-20T21:10:00",
  "images": [{ "id": "018f...", "sortOrder": 1, "objectKey": "task/1/202609/6f1c....png",
               "url": "https://todo.example.com/media/task/1/202609/6f1c....png" }] }
```

`images` 由服务层对当前页**批量**查询后回填，一页只产生 2 次 SQL；数组**已按 `sortOrder` 升序排好**（序号小的在前），前端照序渲染即可。

> **`images[].id`（配图主键）是必需的**：更新任务时 `imageOrder` 的元素就是它（见 ⑦），
> 前端拿不到这个 ID 就没法表达「保留哪些图、怎么排」。
> `GET /api/tasks/{id}` 详情的 `images` 与列表**结构完全一致**（同字段、同按 `sortOrder` 升序），前端复用同一套渲染与排序组件。

**⑦ 新建 / 更新任务** `POST /api/tasks`、`PUT /api/tasks/{id}`

`Content-Type: multipart/form-data`——**配图随任务一起提交**，没有「先上传、后绑定」的两段流程：

| 段 | 内容 |
| --- | --- |
| `data` | 任务本身（JSON），`part` 的 `Content-Type` 为 `application/json` |
| `images` | 配图文件，0~9 个，可重复 |

```jsonc
// data 段（新建）
{ "title": "完成系统设计说明书", "description": "选填", "status": "TODO", "priority": "HIGH",
  "dueDate": "2026-10-01T18:00:00", "refreshRecordedAt": true }
// data 段（更新时多一个字段，给出配图的最终顺序）
{ ..., "imageOrder": ["018f...", "NEW", "018f..."] }
```

- **`imageOrder` 是有序数组**，元素 = 该任务已有配图的 ID 或占位符 `"NEW"`（按出现次序对应 `images` 段的第 1、2… 个文件）。它一次表达三件事：**保留哪些旧图、新图插在哪、最终什么顺序**——拖动排序就靠它；
- 新建：`imageOrder` 可省略（等价于「`images` 段的顺序即展示顺序」）。服务端就地校验图片（≤9 个、格式、单张 ≤10MB），写 MinIO 后在**同一个事务**里插入 `task` 与 `task_image`，按顺序写 `sort_order = 1..N`；
- 更新：未出现在 `imageOrder` 里的旧图删除（**先删对象、再删记录**）；`"NEW"` 按序取 `images` 段的文件插入；随后**把该任务全部配图的 `sort_order` 重编为 `1..N`**。省略 `imageOrder` = 保留全部旧图、新图追加在最后；
- `imageOrder` 里的 ID 必须属于该任务（否则 3005）、**不得重复出现**（同一 ID 写两遍 → 400，同一行没法被赋两个 `sort_order`）；`"NEW"` 个数与 `images` 段文件数必须一致（否则 400）；**单任务配图 ≤9，且单用户图片总数 ≤5000**（否则 2006，两道上限复用同一个码、提示文案区分）；
- 对象写入不在事务内：**落库失败要在同一请求里补偿删除刚写的对象**，补偿也失败就只记日志（孤对象靠人工核对，见 7.7）；
- `refreshRecordedAt`（默认 `true`）为真时把 `recorded_at` 刷成当前时间，为假则保持原值；
- **任务没有 `updated_at`**：界面上的「时间」就是 `recordedAt`。因为列表按 `recordedAt DESC` 排序，刷新它等于把这条任务顶到最前面。

**⑧ 变更状态** `PATCH /api/tasks/{id}/status` → `{ "status": "DONE" }`，置为 `DONE` 写 `completedAt`，从 `DONE` 切走则清空。
**不刷新 `recordedAt`**——"完成"不是"重新记录"，任务在列表中的位置保持不动（只变样式：打钩 + 删除线）。

**⑨ 上传 / 移除头像** `POST /api/users/me/avatar`、`DELETE /api/users/me/avatar`（multipart，字段名 `file`）

头像与任务配图不同：它**不依附于任何表单**，进来即绑定，所以独立成接口。

| 校验 | 规则 | 错误码 |
| --- | --- | --- |
| 裁剪 | **前端**在弹窗里用 1:1 取景框裁成正方形（输出 512×512），服务端不校验比例 | — |
| 非空 | 文件存在且 > 0 字节 | 3001 |
| 大小 | ≤ 10MB（压缩后通常远小于此） | 3002 / HTTP 413 |
| 类型 | 扩展名 + **文件头魔数**双重校验，与白名单不符即拒绝 | 3003 |
| 存储 | 写 MinIO → 同一事务内**删旧行 + 插新行**（`user_avatar.user_id` 唯一）→ 提交后再删旧对象 | 3006 |

移除头像：删记录 + 删对象；本来就没有头像时也返回成功（幂等）。

**⑩ 回收站**

| 接口 | 行为 |
| --- | --- |
| `GET /api/trash/tasks` | 分页列表，元素追加 `deletedAt` 与 `remainingDays`（= `app.trash.retention-days` − 已删除天数，**按配置计算**，不写死 90）；按 `deletedAt DESC` 排序 |
| `POST /api/trash/tasks/{id}/restore` | `deleted_at` 置空，配图不变；失败 2005 |
| `DELETE /api/trash/tasks/{id}` | 删 MinIO 对象 → 删 `task_image` → 删 `task`；失败 2005 |
| `DELETE /api/trash/tasks` | 批量执行上一条，返回 `{ "removed": 12 }` |

**⑪ 统计概览** `GET /api/tasks/stats`（不含回收站）返回
`{ total, todo, inProgress, done, overdue, dueToday, completionRate, trashCount, trashRetentionDays }`。

`trashRetentionDays` = `app.trash.retention-days`——前端拿它渲染「移入回收站，{N} 天内可恢复」的文案
（**不写死 90**，配置改了文案自动跟；`remainingDays` 同理按它计算，见 ⑩）。

**⑫ 后台管理接口**（全部需要管理员 token，鉴权见 7.11）

**登录** `POST /api/admin/auth/login` → `{ name, password, captchaId, captchaCode }`（`name` 是管理员的登录名，唯一），
响应结构与用户登录一致（`{ token, tokenType, expiresInMinutes, admin }`）。
账号不存在与密码错误返回**同一提示**（5001），登录成功时写 `last_login_at`。

**用户列表** `GET /api/admin/users`

| 参数 | 说明 |
| --- | --- |
| `keyword` | 模糊匹配 `email` / `name` / `phone`；为空不过滤 |
| `status` | `NORMAL` / `FROZEN` / `DELETED` 三选一；**不传 = 正常 + 已冻结**（默认不含已注销） |
| `page` / `size` | 分页，规则同 6.6（默认 20，上限 100） |

```jsonc
// records 元素
{ "id": "018f...", "email": "alice@example.com", "phone": "13800000000", "name": "爱丽丝",
  "avatarUrl": "https://todo.example.com/media/avatar/1/202609/6f1c....png",
  "frozenAt": "2026-10-08T10:00:00", "frozenReason": "疑似批量刷接口", "deletedAt": null,
  "taskCount": 123, "taskCountInTrash": 5, "imageCount": 12, "imageCountInTrash": 0,
  "createdAt": "2026-09-20T21:10:00" }
```

`avatarUrl` 由服务层按 `objectKey` 拼接（无头像时为 `null`）；四个计数用**一次条件聚合**拿回
（`count(*) FILTER (WHERE deleted_at IS NULL / IS NOT NULL)`，按当前页的 `user_id IN (...)` 批量），
一页只多 2 次 SQL，不逐行查。**口径**：不带 `InTrash` 的是"在用"的，带 `InTrash` 的是回收站里的，
两者相加 = 该账号的全部数据量。

**用户详情** `GET /api/admin/users/{id}` → 上面元素的全部字段（供详情抽屉展示）。
用户不存在返回 1004。

**改资料** `PUT /api/admin/users/{id}` → `{ "name": "爱丽丝", "email": "a@b.com" }`

- 两个字段都可选，只传要改的；**邮箱撞车返回 1002**（`name` 不参与查重），手机号不在此接口内；
- **不改密码**（走下面的重置接口），但**会刷新 `password_updated_at`**——邮箱就是登录凭证，改完必须让
  旧 token 立即失效，该用户需用**新邮箱**重新登录（前端二次确认里要写清，见 8.9）。

**冻结 / 解冻** `PATCH /api/admin/users/{id}/status` → `{ "frozen": true, "reason": "疑似批量刷接口" }`

- `frozen = true`：写 `frozen_at = now()` 与 `frozen_reason`；该用户**下一个请求就会被拒**（401 + 1006），前端跳登录页并显示原因；
- `frozen = false`：两列置回 `NULL`；用户用原密码正常登录，任务、配图、回收站原样保留；
- `reason` 可选，最长 128 字符。

**重置密码** `PUT /api/admin/users/{id}/password` → `{ "newPassword": "..." }`

- 服务端 BCrypt 后写入，同时把 `password_updated_at` 刷成当前时间 → 该用户**已签发的 token 立即失效**；
- 不需要用户原密码，响应里也不回显密码；
- 管理员**看不到**用户原密码（BCrypt 单向），只能重置。

**注销** `DELETE /api/admin/users/{id}`

- 注销是**软删除，且不可恢复**：写 `deleted_at = now()`，该用户**下一个请求即被拒**（401 + 1007），
  之后登录也返回 1007「该账号已注销」；
- **数据一律保留，但唯一键立即释放**：任务、配图、头像、回收站，以及 `email` / `phone` 的**原值**
  都原样留在行里；唯一性由 `WHERE deleted_at IS NULL` 的**部分唯一索引**表达（见数据库说明书 5.2），
  所以那个邮箱 / 手机号**立刻可以被重新注册或绑定**；
- **没有「恢复」**：注销是终态。要再用只能重新注册——那是**一个全新的账号**，
  与旧账号的任务、图片没有任何关联；
- 已注销的用户在列表里**默认不显示**，把 `status` 选成 `DELETED` 才看得到。

> 后台**没有「物理删除用户」接口**（见 1.2「不做」）：删用户要连带清掉任务、图片与 MinIO 对象，
> 风险远大于收益，且无法撤销。要"停用"就用注销，要"临时堵住"就用冻结。

**新增管理员 / 管理员列表** `POST /api/admin/admins`、`GET /api/admin/admins`

新增体：`{ "name": "ops", "password": "Abcd1234" }`（`name` 是登录名，密码同统一规则，见 ③）

- **任何已登录的管理员都能新增**，后台没有"超管"概念（理由见 7.11）；
- `name` 撞车返回 **5002**；
- **创建后即不可修改**：没有改密、改名、删除、停用接口（见 1.2「不做」）——忘记密码只能手工改库（见 7.11）；
- 列表返回 `{ id, name, lastLoginAt, createdAt }`（**不含任何凭证字段**），用于后台展示"已有哪些管理员"；
- 新增动作记一条 INFO 日志（`adminId`、新管理员名、结果，见第 10 章）。

### 6.6 通用查询约定

- 分页默认 `page=1&size=20`，`size` 上限 100；
- 筛选条件之间是 AND；字符串条件为空时自动忽略，未传即「不限制」；
- 排序默认 `recordedAt DESC`，非法字段回退默认值；
- 除回收站接口外，所有任务查询自动附加 `deleted_at IS NULL`。

分层职责：Controller 只做参数绑定与响应包装；Service 承载业务规则、事务边界、越权校验；Storage / MailSender 封装外部服务；Mapper 只做数据访问（一律 `extends BaseMapper<T>`，单表用条件构造器、复杂 SQL 写注解或 XML）。

### 7.2 通用层

- **统一响应** `ApiResponse<T>`：Java `record`，提供 `ok(data)` / `ok()` / `error(code, message)`；
- **分页**：请求侧 `PageQuery`（page / size / sortBy / sortDirection，内置上限校验）转成 MyBatis-Plus 的 `Page<T>`；查询侧返回 `IPage<T>`，由 `PageResult<T>` 转成只含 5 个字段的对外结构。分页插件在 `MybatisPlusConfig` 注册；
- **异常**：可预期问题抛 `BizException(ErrorCode)`（日志 WARN）；其余异常由 `GlobalExceptionHandler` 兜底（ERROR + 完整堆栈，对外只返回统一文案）；
- **审计字段**：`BaseEntity` 的 `createdAt` / `updatedAt` 用 `@TableField(fill = FieldFill.INSERT / INSERT_UPDATE)` 标注，由 `AuditMetaObjectHandler` 自动填充。**`Task` 不用这两个字段**：它的时间列是 `recordedAt`（映射 `recorded_at`），只在插入时填 `now()`，更新时不动——是否刷新由用户在编辑弹窗里勾选（见 7.6）。

`GlobalExceptionHandler` 映射关系：

| 异常 | HTTP | 业务码 |
| --- | --- | --- |
| `BizException` | 200 | 1xxx / 2xxx / 3xxx / 4xxx |
| 参数校验类（`MethodArgumentNotValidException` 等） | 400 | 400 |
| `MaxUploadSizeExceededException` | 413 | 3002 |
| 方法不支持 / 资源不存在 / 权限不足 | 405 / 404 / 403 | 同 HTTP |
| 其它 `Exception` | 500 | 500 |

### 7.3 鉴权

JWT（HS256），**两套密钥**：用户侧 `app.jwt.secret`、管理员侧 `app.jwt.admin-secret`，
两者各自**启动时校验长度 ≥ 32 字节**，否则拒绝启动。载荷都只放 `sub`（账号 ID）、`iss`、`iat`、`exp`
（管理员 token 额外带 `role: ADMIN`，仅供日志排查用）。**不放 `name`**：它随时可改，而每次请求本来就要查库，取最新值即可。

**两套密钥是硬隔离**：管理员与用户各有独立的 `JwtTokenProvider`，`SecurityConfig` 里是**两条过滤器链**
（`securityMatcher("/api/admin/**")` 一条、其余一条），各自只认自己的密钥（见 7.11）。
因此用户 token 拿到后台**连签名都验不过**，不依赖任何"角色判断写没写对"。

过滤器链：`CorsFilter` → `JwtAuthenticationFilter`（解析 Bearer token 写入 SecurityContext）→ 白名单校验 → Controller。
会话策略 `STATELESS`；关闭 CSRF（无 Cookie 会话）、表单登录、HTTP Basic。

免登录白名单：`/api/verify/**`、`/api/auth/register`、`/api/auth/login`、`/api/auth/password/reset`、
**`/api/admin/auth/login`**、`/v3/api-docs/**`、`/swagger-ui/**`、`/actuator/health`、`/media/**` 以及所有 `OPTIONS`。

`/api/verify/email-code` 虽然免登录，但**强制要求图形验证码**，且带 60 秒间隔与每日 10 次上限。

**当前用户注入**：自定义 `@CurrentUserId` 注解 + `HandlerMethodArgumentResolver`，从 `SecurityContext` 取 `userId`，取不到直接抛 401。业务代码无法「忘记」传用户 ID，水平越权在框架层被堵死。

### 7.4 用户模块

| 用例 | 关键处理 |
| --- | --- |
| 注册 | 校验图形码 → 查重 → BCrypt → 落库 → 签发 token（落库部分单事务）；邮箱码在写库前已于 Redis 消费 |
| 登录 | 校验图形码 → **按 `email` 查（带 `deleted_at IS NULL`）** → BCrypt 比对 → 已冻结 / 已注销的判定放在密码通过之后；邮箱不存在与密码错误返回同一错误码 |
| 找回密码 | 消费邮箱码 → 按邮箱查用户 → 更新密码；查不到用户也返回成功 |
| 更换邮箱 | 消费邮箱码 → 校验新邮箱未被占用 → 更新 |
| 修改密码 | 校验原密码 → 加密新密码 → 前端收到成功后强制重新登录 |
| 头像 | 写 `user_avatar`（同一事务内删旧行 + 插新行），**先提交数据库再删旧对象**——反之可能出现头像 404 |

密码用 BCrypt（自带随机盐，强度 10），列长 128 以便将来升级算法。

### 7.5 验证码与邮件（验证码全部存 Redis）

**Redis 的定位**：只存「短命 + 一次性 + 可丢失」的数据——两个验证码与限流计数；业务数据一律不进 Redis（见第 5 章）。
统一走 `StringRedisTemplate`（不用 JDK 序列化），所有命令封在 `VerifyCodeRepository` 里，业务代码不直接碰 Redis。

| key | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `todone:verify:captcha:{captchaId}` | STRING | 120 秒 | 图形验证码答案；校验用 `GETDEL`，取出即删、一次机会 |
| `todone:verify:code:{scene}:{email}` | HASH（`code` / `attempts`） | 300 秒 | 邮箱验证码；发新码以同 key 覆盖，旧码天然作废 |
| `todone:verify:cd:{scene}:{email}` | STRING | 60 秒 | 发信冷却：`SET NX EX 60`，已存在即拒（4003） |
| `todone:verify:daily:{email}:{yyyy-MM-dd}` | STRING | 到次日 00:00 | 每日发信计数：`INCR` + `EXPIREAT`，超过 10 拒（4004） |

**发信流程**：① 校验图形码（`GETDEL`）→ ② 场景校验（注册 / 换邮箱查重）→ ③ `SET NX EX 60` 冷却 → ④ `INCR` 当日计数 → ⑤ 写验证码（覆盖即作废旧码）→ ⑥ 调 Resend。
**没有落库这一步**——这就是迁到 Redis 最直接的收益。

**校验用一个 Lua 脚本**，一次 RTT、天然原子，替代原来的「SQL 影响行数当 CAS」：

```lua
-- KEYS[1] = todone:verify:code:{scene}:{email}   ARGV[1] = 用户输入   ARGV[2] = 最大尝试次数(5)
local v = redis.call('HMGET', KEYS[1], 'code', 'attempts')
if not v[1] then return 0 end                                     -- 0 不存在 / 已过期 → 4002
if v[1] == ARGV[1] then redis.call('DEL', KEYS[1]) return 1 end    -- 1 通过（删除即消费）
local n = tonumber(v[2] or 0) + 1
if n >= tonumber(ARGV[2]) then redis.call('DEL', KEYS[1]) return 3 end  -- 3 超限作废 → 4005
redis.call('HSET', KEYS[1], 'attempts', n) return 2               -- 2 码错 → 4002
```

**容量与淘汰**：图形码接口免登录，可能被刷。Redis 侧用 `maxmemory 256mb` + `maxmemory-policy volatile-lru`
兜底（本项目所有 key 都带 TTL，淘汰带 TTL 的 key 是安全的）；但那只防**内存**——**画 PNG 是 CPU 密集操作**，
Redis 管不住，所以图形码接口的**请求数**由 Nginx `limit_req`（`/api/verify/**`，见 11.1）在到达后端之前拦住。

**降级策略**：Redis 连接失败或超时 → 验证码类接口返回 **4007（HTTP 503）**，
提示「验证码服务暂时不可用，请稍后重试」，不抛 500。此时注册 / 登录 / 找回密码 / 更换邮箱不可用；
已登录用户的其他功能（任务、回收站、图片）不受影响。

**审计**：原表的 `request_ip` / `used_at` 不再有存储位置，改为**日志留痕**——发码与校验都记
`email + scene + ip + Resend 请求 ID`（**不含验证码明文**，见第 10 章）。Redis 不是审计存储。

**图形码图片仍由 Hutool 生成**（`LineCaptcha`，120×40，4 位字符，8 条干扰线），变的只是答案的存放位置。

**Resend 发信**

`MailSender` 接口只声明 `sendVerificationCode(email, code, scene)`；`ResendMailSender` 用 Spring `RestClient` POST `https://api.resend.com/emails`。

| 关注点 | 处理 |
| --- | --- |
| 异常 | 失败抛 4006，但**已写入 Redis 的验证码不回滚**（TTL 到期自然消失），用户可点重发 |
| 超时 | 连接 3 秒 / 读取 5 秒，避免外部服务拖垮请求线程 |
| 重试 | **不自动重试**：验证码本身有重发按钮，自动重试只会造成重复邮件 |
| 日志 | 只记「成功/失败 + 邮箱 + 场景 + Resend 请求 ID」，**绝不记录验证码明文** |
| 模板 | 三个场景各一套 HTML，样式全部内联（邮件客户端对 `<style>` 支持差） |
| 本地开发 | `LoggingMailSender` 只打日志不发信，不消耗 Resend 配额 |

### 7.6 任务与回收站

- **查询**：用 `LambdaQueryWrapper` 动态拼装——`userId`（强制）、`deletedAt IS NULL`（强制）、`keyword`（title / description 的 OR 模糊匹配）、`status`、`priority`、`onlyUnfinished`，配合 `Page<T>` 分页；
- **软删除禁用 `@TableLogic`**：它会给**所有**查询自动拼上 `deleted_at IS NULL`，回收站将永远查不到数据。改为在 QueryWrapper 里按场景附加 `isNull` / `isNotNull`；
- **配图回填**：查出当前页后收集任务 ID，用 `selectList(in)` 一次查回后按 `task_id` 分组，避免 N+1；
- **越权校验**：`selectById` 后比对 `userId`，失败统一抛「任务不存在」，不区分「没这条」与「不是你的」；
- **删除任务**：只置 `deleted_at`，**不触碰配图**，使恢复时图片完整保留；
- **时间语义（没有 `updated_at`）**：`recorded_at` 插入时写入，编辑时 `refreshRecordedAt` 为真（默认）就刷成当前时间；**变更状态（`PATCH /status`）不刷新它**——勾选完成只是改状态，不把任务顶到最前；`completed_at` 由状态机写入与清空；`deleted_at` 标记回收站。列表按 `recorded_at DESC`，刷新即置顶；
- **统计**：用 `selectCount(wrapper)` 走数据库聚合，全部命中索引，不把明细拉回内存聚合。

**回收站**

- 列表：把软删除条件翻转为 `deleted_at IS NOT NULL`，按 `deletedAt DESC` 排序；
- 彻底删除（单条 / 清空共用）：删 MinIO 对象 → 删 `task_image`（按 `task_id`）→ 删 `task`。**MinIO 删除失败只记日志不阻断**——孤儿文件可事后核对，优先保证用户侧「删除成功」的确定性；
- **到期自动清理**：软删除满 **90 天**后由 `TaskCleanupJob` 物理清理（见 7.8）；在此之前用户可随时恢复。

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `app.task.max-images` | 9 | 单任务配图上限 |

### 7.7 文件模块

元数据分两张表：`user_avatar`（头像，一用户一行）与 `task_image`（配图，一任务多行）。两者提交时机不同——头像自成一次请求，配图随任务表单一起提交；**两张表都没有临时态**。配图另有展示序号 `sort_order`（同一任务内从 1 开始，小的排前面），**每次保存按提交顺序重编为 `1..N`**，因此支持拖动排序（见 6.5 ⑦）。

**对象命名**：`{场景}/{userId}/{yyyyMM}/{uuid}.{ext}`，例如 `task/1/202609/6f1c....png`。
文件名用 UUID，不含原始名，杜绝路径穿越与中文乱码；月度目录避免单目录对象过多。

**前端先把图处理好再传**（后端不做任何图像处理）：

| 场景 | 处理 |
| --- | --- |
| 通用 | 选图后立即在浏览器里判断：**长边 > 1920px 或体积 > 1MB** 时用 canvas 重绘为长边 1920、质量 0.85 的 JPEG / WebP；**GIF 跳过**（压缩会丢动画），只做大小校验 |
| 头像 | 先弹 **1:1 取景框**（可拖动 / 缩放），确认后裁出正方形、输出 512×512，再走上面同一套压缩 |

这么做省带宽，也不用在后端引入图像处理依赖；代价是「只能相信客户端压过了」——所以**体积与魔数在后端仍然硬校验**。

**上传校验**：空文件 → 大小（≤10MB）→ 扩展名白名单 → **读取文件头魔数**与扩展名比对 → 写 MinIO → 落元数据行。
只信任客户端传来的 `Content-Type` 是不可靠的（可随意伪造）。

**写对象不在事务内，只做「补偿删除」**：MinIO 写成功后若落库失败，**在同一个请求里删掉刚写的对象**；
连补偿删除也失败时只记 ERROR 日志，那种孤对象只能靠人工按巡检结果核对——系统里没有任何后台清理任务。

| 格式 | 魔数（十六进制前缀） |
| --- | --- |
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| GIF | `47 49 46 38` |
| WEBP | `52 49 46 46` …（第 9~12 字节为 `57 45 42 50`） |

**图片访问**：桶设为匿名只读，Nginx 反代 `/media/` → MinIO。

- 桶策略**只允许 `s3:GetObject`，不允许 `s3:ListBucket`**，对象无法被枚举；
- 对象键含 UUID，不可猜测；
- Nginx 统一设 `Cache-Control`，浏览器可缓存，减轻后端与 MinIO 压力；
- 同时加 **`X-Robots-Tag: noindex`**（图片匿名可读，避免被搜索引擎收录）与
  **`Referrer-Policy: no-referrer`**（避免被第三方页面外链时泄露来源地址）；
- **上传/删除只走后端 SDK**（凭证仅后端持有），浏览器只能读。

若将来要求「图片必须登录且仅本人可见」，可改为后端代理读取（新增 `GET /api/files/{objectKey}` 校验归属后流式返回），当前不做。

### 7.8 数据清理：只有一个定时任务

**系统里唯一的自动清理**是回收站超期清理——`task/job/TaskCleanupJob`，启动类加 `@EnableScheduling`：

| 项 | 设计 |
| --- | --- |
| 触发 | `@Scheduled(cron = "0 30 3 * * ?")`，每天 03:30 |
| 范围 | `deleted_at < now() - 90 天` 的任务 |
| 动作 | 删 MinIO 对象 → 删 `task_image` 记录 → 删 `task`（顺序理由见 7.6） |
| 批次 | 每批 200 条、独立事务；单条失败记 ERROR 后继续，一条坏数据不阻塞整批 |
| 幂等 | 按主键删除，天然幂等，重复执行无副作用 |
| 日志 | 每批记 INFO（条数 + 耗时），便于人工核对 |
| 配置 | `app.trash.retention-days`，默认 90 |

单机单实例，无需分布式锁；应用没启动时任务不跑，下次启动照常补上（判据是 `deleted_at`，与执行次数无关）。

**为什么只需要这一个**：图片没有临时态（见 7.7）；验证码靠 Redis 的 TTL 自己消失；
`user_avatar` 与 `task_image` 都只有「插入」和「被删除」两种状态——**没有第二种"到点必须清"的数据**。
再加定时任务，只会多出「应用没启动时漏跑」的排查面。

**三条纪律**：

1. **删除顺序为先 MinIO 对象、后数据库记录**：对象删失败就跳过该条（下轮再试或人工核对），避免「有记录无对象」的悬挂数据；
2. **单条失败不阻塞整批**：记 ERROR 后继续处理下一条，本轮仍算跑完（下一轮还会碰到它）；
3. **不新增第二个定时任务**：将来若真出现「到点必须清」的数据，先想清楚它为什么不能惰性处理（见 12 章）。

### 7.10 事务

| 场景 | 事务 |
| --- | --- |
| 查询类 | `@Transactional(readOnly = true)` |
| 注册 | `REQUIRED`：查重 + 建用户 + 签发 token。**验证码消费在 Redis，不在事务内**，且放在写库之前 |
| 找回密码 / 更换邮箱 | `REQUIRED`：改密 / 换邮箱的落库部分；验证码同样先在 Redis 消费 |
| 任务新建 / 更新 | `REQUIRED`：任务落库与配图的插入 / 删除（`task_image`）必须原子；MinIO 的写在事务外，失败时补偿删除 |
| 头像上传 / 移除 | `REQUIRED`：删旧行 + 插新行（或删行）在同一事务内；MinIO 对象删除放在提交后 |
| 彻底删除 / 清空 | `REQUIRED`；MinIO 对象删除放在事务提交后，避免长事务持有连接 |
| 发送邮箱验证码 | 写 Redis 不在事务内；**邮件发送放在流程之外**（外部 IO 不阻塞） |
| 回收站定时清理 | 每批独立事务；单条失败不影响其余记录 |
| 配图上传 | 与任务落库同一事务；**MinIO 写成功但事务回滚时，在同一请求里删掉刚写的对象** |

并发冲突（同一用户同时改同一条任务）采用**最后写入生效**，不引入乐观锁。
对象存储的写入无法纳入数据库事务，因此采用「先写对象、后写元数据」的顺序；落库失败时在同一请求里补偿删除对象（见 7.7）。

### 7.11 管理员与后台鉴权

**两套密钥、两条过滤器链**：用户侧 `app.jwt.secret` + `userJwtProvider`，
管理员侧 `app.jwt.admin-secret` + `adminJwtProvider`，两者完全独立。
`SecurityConfig` 配两条 `SecurityFilterChain`，用 `securityMatcher` 按路径前缀分家：

| 链 | 匹配 | 过滤器 | 授权 |
| --- | --- | --- | --- |
| 后台链 | `/api/admin/**` | `AdminJwtAuthenticationFilter`（**只认管理员密钥**） | `/api/admin/auth/login` 放行，其余 `hasRole('ADMIN')` |
| 前台链 | 其余全部 | `UserJwtAuthenticationFilter`（**只认用户密钥**） | 7.3 的白名单放行，其余 `hasRole('USER')` |

**为什么值得多配一个密钥**：签名本身就是第一道门——用户 token 拿到后台**验签就失败**（401），
不依赖任何"角色判断有没有写对"；反过来管理员 token 也签不出用户接口的会话。
密钥还能各自轮换：重置管理员密钥不会牵连任何用户会话。

前端把两者存在互不相干的 localStorage key 里（`todone_token` / `todone_admin_token`）。

**每次请求多查一次库，换来「冻结 / 注销立即生效」**：过滤器验签通过后取一次账号
（`app_user` 或 `admin_user`），做四项检查：

| 检查 | 不通过时 |
| --- | --- |
| 账号是否存在 | 401（`RestAuthenticationEntryPoint`，统一文案「登录状态已失效，请重新登录」） |
| `frozen_at` 是否为空 | 401 + 业务码 **1006**（提示里带上 `frozen_reason`） |
| `deleted_at` 是否为空 | 401 + 业务码 **1007**「该账号已注销」 |
| token 的 `iat` 是否 ≥ `password_updated_at` | 401（改密、管理员重置密码或改资料后，旧 token 立即作废）。**比较前先把 `password_updated_at` 截断到秒**——`iat` 只有整秒精度，比微秒会快一秒，比微秒直接比会让新签发的 token 当场失效 |

**200 在线 / 20 QPS 的量级下**，每请求多一次主键查询（走主键索引）的开销可以忽略——换来的是
**不需要 token 黑名单或会话表**，状态只在数据库里存一份、永远是准的。（真要优化也只是把这层挪进 Redis，百人量级用不着。）

**后台的可见范围：只见账号，不见内容**。后台接口只读写 `app_user` 的账号字段
（`email` / `phone` / `name` / `frozen_*` / `deleted_at` / `password_updated_at`），以及 `user_avatar`
的 `object_key`（**只用来拼 `avatarUrl`**）；**不查询 `task` 与 `task_image` 的任何一行**——
用户的**任务与配图**对管理员完全不可见。
**头像不算隐私边界**：它是账号资料的一部分（跟名字同级），用来让管理员认人；而列表里的
「任务数 / 图片数」（含各自在回收站中的数量）只是**条件聚合的计数**，不返回任何内容本身（见 1.2「不做」）。
实现上：`AdminUserController` **不注入 `TaskMapper`**，`FileMapper` 里也只许读 `user_avatar`、禁碰 `task_image`。

**管理员引导创建**（`admin/service/AdminBootstrap`，实现 `ApplicationRunner`）：

- 启动时若 `admin_user` 表为空，读 `app.admin.bootstrap-name` / `app.admin.bootstrap-password`
  创建第一个管理员，记一行 INFO；
- 表非空则**什么都不做**（不覆盖、不重置密码）；
- 两个配置都为空时跳过，并 WARN 提醒「尚无管理员，请在 `.env.prod` 配置初始管理员」；
- 因此首个管理员的密码**只存在于服务器 `.env.prod`**，不进库、不进代码（部署步骤见 11.3）。

**管理员只能新增，不能修改**：后台有一个「新增管理员」入口（见 6.5 ⑫ 与 8.9），但**没有**改密、改名、
删除、停用——「谁能改管理员密码」本身需要一套权限模型（要不要超管？允许自助改密吗？），
而 1~3 名管理员的量级不值得引入这套复杂度。规则因此极简：**任何已登录管理员都能新增管理员，
但谁也改不了已有管理员**。
忘记管理员密码只能手工改库：`UPDATE admin_user SET password = '<BCrypt 密文>', password_updated_at = now()`
——**两者必须一起改**，只改密码不刷新 `password_updated_at` 的话，该管理员的旧 token 仍然有效（见 7.3）。

### 8.4 请求封装

`api/http.ts` 统一处理五件事：注入 `Authorization` 头；`code !== 200` 时提示并 reject；
HTTP 401 清除 token 并跳登录页；413 / 3002 给出「图片不能超过 10MB」的明确提示；按状态码给出网络异常提示。

**token 按请求路径选**：`/api/admin/**` 用 `todone_admin_token`、401 时跳 `/admin/login`；
其余接口用 `todone_token`、401 时跳 `/login`。**清 token 也要对应清**，
后台掉线不会把用户踢出去，反之亦然（见 7.11）。

对外暴露 `request<T>(config)` 与 `upload<T>(url, file)` 两个方法，业务侧拿到的直接是 `data`。

| 数据 | 按 `recordedAt DESC` 取，首屏 `page=1&size=20`；滚动到底加载下一页，取不满一页即到底 |
| 筛选切换 | 清空已加载数据并从第 1 页重取，滚动位置回到顶部 |
| 卡片内容 | 标题、优先级与状态文字、截止时间、描述截断 3 行、配图缩略图（最多显示 3 张 + 余数） |
| 加载态 | 首屏骨架屏；触底加载时显示行内 loading，避免重复触发 |

> 瀑布流只改变**展示**，查询仍是「`user_id` + `deleted_at IS NULL` + `recordedAt DESC`」，
> 沿用现有索引 `idx_task_user_deleted_recorded`，数据库侧无需改动。

**动效**

统一取 `--dur-fast` / `--dur-base` / `--ease` 三个变量，**只动 `transform` 与 `opacity`**（不触发布局重排）。

| 场景 | 效果 |
| --- | --- |
| 新增任务 | 淡入 + 从 `scale(.98)` 回到 1（200ms）；其余卡片平滑让位（`TransitionGroup` + FLIP） |
| 删除任务 | 先播 200ms 淡出 + 高度收缩，再移除数据，其余卡片补位 |
| 勾选完成 | 对勾描边动画 + 标题删除线自左向右展开（200ms），文字同步转次要色 |
| 状态 / 优先级变更 | 文字与描边颜色 150ms 过渡，无位移 |
| 筛选 / 排序切换 | 瀑布流整体淡出→淡入（150ms），避免卡片跳动 |
| 加载更多 | 新卡片错峰淡入（每张延迟 30ms，最多 5 张）；骨架屏与内容 150ms 交叉淡出 |
| 弹窗与遮罩 | 用 Element Plus 默认（`fade` + `scale`），遮罩 200ms |
| 上传进度 | 进度条宽度 200ms 过渡；成功后缩略图淡入 |
| 主题切换 | 见「深色模式」的切换动效 |
| 减少动效 | 命中 `prefers-reduced-motion: reduce` 时把 `--dur-fast` / `--dur-base` 置 0，动画退化为瞬时 |

**实现约定**：列表增删一律用 `<TransitionGroup>` 并给每项稳定 `key`（任务 ID）；不用 CSS `@keyframes` 写一次性动画；组件里不写死毫秒数，一律取变量。

**落地要求**：页面上不存在「主操作 / 危险色 / 状态色」之外的彩色；无渐变；列表区域无阴影与圆角外框，靠 1px 分隔线划分；统计信息用文字，不做大色块数字卡片；同一屏字号层级不超过 4 级。**浅色与深色下都必须满足以上全部。**

## 9. 安全设计

**认证与授权**：无状态 JWT（HS256），`Authorization: Bearer <token>`；**两种角色、两套密钥**——用户（有效期 24 小时，`APP_JWT_SECRET`）与管理员（2 小时，`APP_JWT_ADMIN_SECRET`），两个密钥各自长度 ≥ 32 字节、互不通用；业务数据遵循「本人资源」模型，以 `user_id` 隔离（后台不读业务数据，只读写账号状态）。

**水平越权**：入口由 `@CurrentUserId` 强制注入；所有列表/统计的第一条件固定为 `userId`；单条操作先查后比对归属，失败统一返回「资源不存在」；图片绑定校验 `user_id`；回收站操作同时校验 `user_id` 与 `deleted_at`。细节见 7.3 与 7.6。

**密码**：BCrypt 加盐哈希，不可逆；登录失败统一提示（防枚举）；改密需验证原密码。

**风险与防护**

| 风险 | 防护 |
| --- | --- |
| 上传恶意脚本 / 路径穿越 | 仅 4 种图片格式 + 扩展名与文件头魔数双重校验；对象键由服务端生成，不拼接用户输入 |
| 撑爆存储 | 单文件 ≤10MB（前端还会先压到长边 1920）、单任务 ≤9 张、**单用户图片总量 ≤5000 张**、单用户头像 1 张；前端 / 后端 / Nginx 三层限制 |
| 图片越权读写 | 桶只允许匿名 `GetObject`（禁 `ListBucket`），写权限仅给后端服务账号 |
| 脚本刷接口 / 邮件轰炸 | 登录、注册、发码三处强制图形验证码（答案不下发）；再叠加 Redis 的 60 秒冷却与每邮箱每日 10 次计数 |
| 暴力猜码 / 重放 | 6 位数字 + 5 分钟 TTL + 单条最多 5 次尝试；Lua 脚本「比对即删除」，天然防并发复用 |
| Redis 自身 | 仅容器内网可达（不映射宿主端口）、`--requirepass` 鉴权、**不持久化**（重启丢码，用户重发即可）；验证码明文不进日志 |
| 账号枚举 | 找回密码不校验邮箱是否存在；邮箱统一转小写比对；管理员登录失败只回统一文案（5001） |
| 后台越权 | 管理员与用户用**两套独立密钥**（见 7.11）：用户 token 拿到后台验签即失败（401），反向同理；路径前级再由两条过滤器链各管一段 |
| 管理员爆破 | 后台登录同样强制图形验证码（答案不下发）；无账号锁定，靠强密码 + 图形码 |
| 冻结账号的残留会话 | 过滤器每次请求校验 `frozen_at` 与 `password_updated_at`，**冻结 / 重置密码 / 改资料后旧 token 立即作废** |
| 密钥与日志泄漏 | Key 只存服务器 `.env.prod`（权限 600、不进版本库）经环境变量注入；验证码明文一律不入日志 |
| 密钥轮换与隔离 | 用户与管理员**两套独立密钥**（见 7.11）：轮换管理员密钥不影响任何用户会话；两者都 ≥ 32 字节且必须不同，启动时校验 |

**传输与配置**：全站 HTTPS（Nginx 终止 TLS + HSTS）；安全组只放行 22 / 80 / 443，PostgreSQL、MinIO、后端只在容器网络内可达；SSH 仅密钥登录、禁止 root；CORS 生产同域无需跨域，需要时用白名单而非 `*`；500 只返回统一文案，堆栈仅落日志；生产关闭 Swagger UI 并由 Nginx 屏蔽 `/v3/api-docs`。

## 11. 部署与运维

> **当前是设计阶段，本章只记要点**：部署脚本、Nginx 配置、证书与初始化命令等到真正部署时再补全，
> 这里留下「必须记住的事」，避免实现时返工。

### 11.1 形态、服务器与 Nginx 要点

单台 Ubuntu 22.04 LTS，**规格分档见 4.3**（起步 2C4G / 百人档 4C8G），安全组入站只放行 22 / 80 / 443，
出站需可达 `api.resend.com:443`。

**五个容器直接 `docker run` 启动，不使用 Docker Compose**——服务就这么几个，编排带来的收益不值得多一层工具；
启动参数（网络、数据卷、`--restart unless-stopped`、`--env-file`）统一由一个 `deploy.sh` 维护。

| 容器 | 说明 | 对外端口 |
| --- | --- | --- |
| `nginx` | 唯一入口：静态资源、`/api` 反代 backend、`/media` 反代 MinIO | 80、443 |
| `backend` | Spring Boot fat jar，JVM `-Xmx` 见下（起步 1G / **百人档 2G**） | 仅内网 8080 |
| `postgres` | 数据卷 `pg_data` | 仅内网 5432 |
| `minio` | 数据卷 `minio_data` | 仅内网 9000 |
| `redis` | 验证码与限流计数，**不持久化**，`maxmemory 256mb` + `volatile-lru` + `requirepass` | 仅内网 6379 |

**内存分配**（百人档）：JVM `-Xmx2048m`、PostgreSQL `shared_buffers 1GB`、MinIO ≈300M、Redis ≤256M、
Nginx ≈100M、系统 ≈600M，合计约 **4.4GB**——这就是百人量级要选 **8G 内存**的原因；
起步档各项减半（JVM 1G / `shared_buffers` 512MB），合计约 2.9GB，4G 内存刚好。

除了内存，还有两处参数要跟着人数调：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| HikariCP `maximum-pool-size` | **20**（默认 10） | 20 QPS × 平均 30ms ≈ 0.6 个连接，10 个本来也够；留余量给慢查询与回收站定时任务。PostgreSQL 侧 `max_connections` 保持默认 100（见数据库说明书 10.1） |
| Nginx `limit_req` | **`/api/auth/**`、`/api/admin/auth/login`、`/api/verify/**`** 上 `rate=10r/s burst=20` | **公网开放 + 开放注册之后必须加**：挡住撞库与批量注册；**后台登录同属高价值入口**（且无账号锁定）；**`/api/verify/**` 防的是画图耗尽 CPU**（见 7.5）；静态资源与 `/media/**` 不限 |

**Nginx 六条要点**（配置部署时再写全）：SPA 必须 `try_files $uri $uri/ /index.html` 回退
（否则刷新 `/tasks` 这类子路由 404）；`client_max_body_size 12m`（略大于应用层 10MB）；
生产 `deny all` 掉 `/actuator/` 与 `/v3/api-docs`；HTTPS 用 Let's Encrypt（webroot 申请 + cron 续期）；
`/media/` 反代 MinIO 并设长缓存 + **`X-Robots-Tag: noindex` 与 `Referrer-Policy: no-referrer`**（见 7.7）；
**`/api/auth/**`、`/api/admin/auth/login` 与 `/api/verify/**` 配 `limit_req` 限流**（公网 + 开放注册的前提，见上表）。

### 11.2 配置：两个 yaml、两个 .env

**所有账号、密码、密钥与可变设置一律写在 `.env` 里**，代码与 yaml 只引用变量名（如 `${DB_PASSWORD}`）。
仓库里只放 `.env.example`；真实 `.env` 权限 600 且进 `.gitignore`（见附录 C 的键名清单）。

| 文件 | 用途 | 谁读 |
| --- | --- | --- |
| `application.yaml` | 公共配置 + **开发**默认值：本地数据源、`StdOutImpl` 打 SQL、Swagger 开、邮件只打日志 | 后端（默认 profile） |
| `application-prod.yaml` | **生产**覆盖：数据源指向容器、SQL 日志关闭、Swagger 关闭、邮件真发 | 后端（`SPRING_PROFILES_ACTIVE=prod`） |
| `.env.dev` | 本地开发的密钥与连接串（可用弱口令） | IDE 运行 / `docker run --env-file .env.dev` |
| `.env.prod` | 服务器上的真实值（强随机密钥、域名、Resend Key） | `deploy.sh` 里 `--env-file .env.prod` |

**两份 yaml 的差异只有四类**：数据源地址、SQL 日志、Swagger 开关、邮件发送方式
（开发用 `LoggingMailSender` 把邮件内容打进日志，生产用 `ResendMailSender`）。
**两份 `.env` 的键名完全一致、只有值不同**——切换环境不改代码、不改键名。

### 11.3 首次部署（要点）

1. **本地构建**：`./mvnw clean package -DskipTests`（jar）+ `npm run build`（`dist/`）
2. **上传**到 `/opt/to-done/`：jar、`frontend-dist/`、`deploy.sh`、`nginx/`、`todone.sql`、`.env.prod`
3. **起容器**：`./deploy.sh up`（内部是一串 `docker run`；postgres / minio / redis 不映射宿主端口）
4. **建表**：`docker exec -i postgres psql -U "$DB_USER" -d "$DB_NAME" < todone.sql`（整份执行，见数据库说明书 9.3）
5. **初始化两件外部资源**：MinIO 建桶 `to-done` 并设匿名只读策略（**只给 `s3:GetObject`，不给 `ListBucket`**）；
   Nginx 起来后用 Let's Encrypt（webroot）申请证书，配 cron 自动续期
6. **创建首个管理员**：`.env.prod` 里设 `ADMIN_BOOTSTRAP_NAME` / `ADMIN_BOOTSTRAP_PASSWORD`，
   以及 `APP_JWT_ADMIN_SECRET`（`openssl rand -base64 32`，**必须与 `APP_JWT_SECRET` 不同**）；
   启动 backend 后应用发现 `admin_user` 为空即自动创建。因为**已有管理员不可修改、不可删除**（见 1.2 与 7.11），
   这个初始密码就是该管理员的长期密码——**请直接设一个强密码**，并把 bootstrap 变量从 `.env.prod` 删掉
   （它们只在表为空时生效，留着只是让明文密码多停留）

**首个管理员只在表为空时创建**：`admin_user` 里已有行时引导逻辑什么都不做，也不重置密码——
所以重启、升级都不会把你改过的管理员密码覆盖回 `.env.prod` 里的初始值（见 7.11）。

### 11.4 邮件（Resend，账号与域名已就绪）

Resend 账号**已注册**、发信域名**已绑定并验证通过**，部署时只需把两个值写进 `.env.prod`：
`RESEND_API_KEY` 与 `MAIL_FROM`（`To_Done <no-reply@mail.example.com>`，邮件走独立子域名，与主站隔离）。

发信出问题时的排查顺序：域名是否仍为 Verified → `dig TXT send.mail.<域名>` 记录是否生效 →
`RESEND_API_KEY` 是否已注入容器（403）→ Key 与域名是否同一账号（403 / 422）→
后端日志里的 Resend 请求 ID → 对方垃圾邮件目录。

### 11.5 升级、备份与日常运维

- **升级**：备份数据库 → 若有表结构变更，先在库上执行 `ALTER` 并把改动改写回 `todone.sql` → 换 jar 与前端产物
  → 重启 backend 容器 → 看日志与 `/actuator/health`。
- **回滚**：换回上一版产物即可。表结构变更遵循「**只做加法**」（不删列、不改类型），所以回滚不必回滚数据库。
- **备份**：`pg_dump -Fc` 每日 03:00（本机留 14 天、异地留 30 天），MinIO 用 `mc mirror` 增量同步，**Redis 不备份**
  （只放 5 分钟生命周期的验证码，丢了让用户重发）。RPO ≤ 24h、RTO ≤ 2h，上线后一个月内做一次恢复演练。
  详细命令与巡检 SQL 见《数据库设计说明书》第 10 章。
- **日常运维**：`docker logs -f --tail=200 backend` 看后端日志、`docker restart backend` 重启单个服务、
  `docker stats --no-stream` 看资源、`docker exec -it postgres psql -U $DB_USER -d $DB_NAME` 进库；
  MinIO 控制台（9001）不对外开放，需要时走 SSH 隧道。

## 12. 开发规范

**后端**

- 4 空格缩进；类/方法写 Javadoc 说明「为什么」而非「是什么」；
- DTO 用 `record`，实体用普通类（MyBatis-Plus 需要无参构造与 setter 完成映射）；**不使用 Lombok**；
- 实体直接持有 `user_id` 等标量引用列，不做对象嵌套；**数据库不建外键**，父行的存在性与删除时的子行处理由 Service 层在事务内显式保证；
- Mapper 一律 `interface XxxMapper extends BaseMapper<Xxx>`；单表查询用条件构造器，复杂 SQL 写 `@Select` 或 XML；
- **SQL 只允许 `#{}` 预编译占位，禁止 `${}` 拼接**；动态排序字段必须走白名单（`PageQuery.sortBy` 的校验就属于这类）；
- 实体字段用 `@TableField` 显式声明列名映射，主键用 `@TableId`；审计字段交给 `MetaObjectHandler` 填充；
- Controller 方法签名把 `@CurrentUserId Long userId` 放第一位；
- **接口文档**：Controller 用 `@Tag` / `@Operation`、DTO 用 `@Schema` 标注，新增或修改接口必须同步注解，保证 Swagger UI 与实现一致（见 7.9）；
- 新增错误码必须登记到 `ErrorCode`，禁止硬编码数字；
- Service 不直接依赖 MinIO SDK（走 `ObjectStorage`）与 Resend（走 `MailSender`）；
- 任务相关查询必须显式处理 `deleted_at` 条件，回收站查询同理（`isNotNull`）；
- **定时任务只允许一个**：回收站超期清理（`TaskCleanupJob`，见 7.8）。没有别的清理任务——图片没有临时态、验证码靠 Redis 的 TTL，不要新增定时任务。
- **写 `app_user` 只允许在 `user` 模块**：后台的冻结 / 解冻 / 注销 / 重置密码 / 改资料一律走 `UserAdminService`，
  不允许在 `admin` 模块里直接注入 `UserMapper`（见 4.2）。管理员表的读写则只在 `admin` 模块内。
- **写 `admin_user` 只允许 INSERT**：只有 `AdminBootstrap`（首启引导）与 `AdminService.createAdmin`（后台新增）
  两处能写这张表，**不提供任何 UPDATE / DELETE 路径**（见 1.2「不做」与 7.11）。
  手工改库换密码时必须同时刷新 `password_updated_at`，否则旧 token 不会失效。
- **两套密钥不可混用**：用户侧只用 `UserJwtProvider`、管理员侧只用 `AdminJwtProvider`；
  `SecurityConfig` 两条链的 `securityMatcher` 不要放宽成更宽的匹配，否则隔离就没了（见 7.11）。
- **所有邮箱 / 手机号查重必须带 `deleted_at IS NULL`**：唯一性由**部分唯一索引**保证（见数据库说明书 5.2），
  漏掉这个条件会把已注销账号误判成"已被占用"。涉及四处：注册（`/api/auth/register`）、
  登录（按邮箱查账号）、更换邮箱（`PUT /api/users/me/email`）、改资料里的手机号（`PUT /api/users/me`）。
  **`name` 不查重**（它不唯一，登录也不用它）。
- **Redis 只能在 `VerifyCodeRepository` 里用**：业务代码禁止直接注入 `RedisTemplate`；key 必须带 `todone:` 前缀、**必须设 TTL**（禁止存永不过期的 key），缓存业务数据一律不做。
- **所有业务查询必须以 `user_id` 为首要条件、并落在索引上**：这是**多用户下的第一红线**——它同时是越权防线
  与性能防线（20 QPS 配上全表扫描会立刻拖垮单机）。新写 SQL 前先对照索引清单（数据库说明书 5.1）。
- **后台不得读业务数据**：`admin` 模块只允许碰 `app_user`、`admin_user` 与 `user_avatar`（后者只为拼 `avatarUrl`）；
  **不得注入 `TaskMapper`**，也不得经 `FileMapper` 碰 `task_image`；用户详情里的四个计数（在用 + 回收站）
  用**条件聚合**（`count(*) FILTER`）拿回，不取任何内容（隐私边界见 7.11 与 1.2「不做」）。
- **数据库不写枚举 `CHECK`**：`status` / `priority` / `sort_order` 的取值与范围一律由后端枚举 + 入参校验
  保证（见数据库说明书 1.2 原则 4）。新增枚举值只改 Java 枚举与校验，**不动 DDL**；库侧只保留
  `NOT NULL` 与 `UNIQUE`。

**前端**

- 2 空格缩进、单引号、无分号；
- 组件用 `<script setup lang="ts">`，props 用泛型声明；
- 所有接口调用必须经过 `src/api/`，组件内禁止直接用 axios；
- 类型统一放 `types/index.ts`，字段名与后端 DTO 一致；
- 颜色、圆角、间距一律用 CSS 变量，禁止在组件内写死色值。

**表结构变更**

改表流程见《数据库设计说明书》9.2~9.4：手工 `ALTER` → 改写回 `todone.sql` 的 `CREATE TABLE` 定义 → 同步更新该文档。**只做加法**（不删列、不改类型）。

**分支与提交**

`main` 稳定分支，`feature/xxx` 功能，`fix/xxx` 修复。提交信息用约定式：`feat: 任务支持配图`、`fix: 修正回收站删除时间`。

**接口变更流程**

先改本文档第 6 章 → 再改后端 DTO 与实现（同步 Swagger 注解）→ 最后同步前端 `types` 与调用代码。变更需向后兼容，禁止直接修改既有字段语义。

### 附录 D：文件上传规则

| 项 | 规则 |
| --- | --- |
| 允许格式 | `jpg` / `jpeg` / `png` / `webp` / `gif` |
| 单文件大小 | ≤ 10MB（前端压缩后通常远小于此） |
| 自动压缩 | 长边 > 1920px 或体积 > 1MB → **前端**压到长边 1920、质量 0.85（WebP / JPEG）；**GIF 不压** |
| 头像裁剪 | **前端**弹 1:1 取景框，裁成 512×512 的正方形后再压缩上传 |
| 字节数 | **不落库**：`user_avatar` / `task_image` 都没有 `size_bytes`（见数据库说明书 4.3 / 4.4） |
| 单任务配图 | ≤ 9 张 |
| **单用户图片总量** | **≤ 5000 张**（该用户所有任务的配图合计；超限返回 2006）——防止单个用户合法地占满磁盘 |
| 用户头像 | 1 张（再次上传即替换） |
| 校验方式 | 扩展名 + 文件头魔数双重校验 |
| 对象命名 | `{avatar\|task}/{userId}/{yyyyMM}/{uuid}.{ext}` |
| 上传接口 | 任务新建 / 更新（multipart 的 `images` 段）、`POST /api/users/me/avatar` |
| 访问方式 | `GET https://{域名}/media/{objectKey}`（Nginx 反代 MinIO） |
| 图片寿命 | 没有临时文件：配图随任务提交即绑定、头像上传即绑定，两者都只等着被删除 |
| 随任务软删除 | 配图保留，恢复任务后仍可见 |
| 随任务彻底删除 | 配图对象与记录一并删除 |

### 附录 E：术语与前端路由对照

| 概念 | 数据库 | 后端接口 | 前端路由 |
| --- | --- | --- | --- |
