# 后端修改说明（前端联调发现的问题）

> 只列**问题**——需要后端改或确认的事。已修复的条目不保留。
> 时间 = 前端发现该问题的时刻（本地时间）。联调环境：后端 8081，前端 `http://localhost:5173`。

1. **2026-10-13 16:00** · 任务新建 / 更新的请求体：真实请求是 `multipart/form-data`，Swagger 却声明成 `application/json`。
   现状（2026-10-14 复核）：`POST /api/tasks` 与 `PUT /api/tasks/{id}` 的 `requestBody.content` 只有 `application/json`，
   它的 schema 里能看到 `data` 与 `images` 两个属性名，但媒体类型不对。
   实测：前端发的是 multipart —— `data` 段（`application/json` 的任务 JSON）+ `images` 段（0~9 个文件），
   服务端正常落库并返回预签名直链（一次新建 2 张图成功，含压缩后的 JPEG 与 GIF）。
   影响：联调者照文档会按 JSON 发（那样传不了文件），或以为配图不能随任务提交。
   期望：把这两个接口声明成 `multipart/form-data`：`data` 标 `application/json`、`images` 标二进制数组并写明最多 9 张。

2. **2026-10-13 16:00** · `TaskCreateRequest` 缺 `imageOrder`（`TaskUpdateRequest` 里有）。
   详情：更新时前端用 `imageOrder` 表达配图顺序（已有图给 id、新图占位 `'NEW'`、空数组 = 删光配图），
   文档里有、行为也对得上；新建时前端按同一约定传 `['NEW', ...]`，接口不报错且两张图都落库，
   但**这个字段不在 `TaskCreateRequest` 里** —— 顺序是否真按 `imageOrder` 生效无从确认（也可能是按 part 顺序）。
   期望：`TaskCreateRequest` 补 `imageOrder`；若新建只认 part 顺序，请在文档里写明，我把前端多余的字段去掉。

3. **2026-10-14 21:39** · `POST /api/auth/register` 把 `captchaId` / `captchaCode` 列为**必填**，与「图形码只在获取邮箱验证码时用一次」的定稿冲突。
   实测：不带这两个字段 → `400 请求参数不合法`；带一张无效的 → `4001 图形验证码错误或已失效`。
   冲突点：图形码是**一次机会** —— 发邮箱验证码时已经把它消费掉了，注册不可能复用同一张；
   前端按定稿只在「获取验证码」时弹图形码、注册不再弹第二次，也就没有可用的图形码可传，于是注册请求会被判 400。
   期望：注册接口去掉图形码校验（`captchaId` / `captchaCode` 改为可选并忽略）—— 邮箱验证码已经证明邮箱可用，防刷留在发信那一步就够了。
